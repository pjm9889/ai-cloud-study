LangGraph 개요

AI Agent가 단순한 질문·응답을 넘어 분기, 반복, 승인, 복구, 병렬 작업을 수행해야 할 때 LangGraph가 왜 필요한지 이해합니다.

0. LangGraph는 왜 필요한가?

LangGraph를 한 문장으로 설명하면

LangGraph는 LLM을 기반으로 상태를 유지하고(Stateful), 여러 단계에 걸쳐 작동하는 멀티스텝(Multi-step) 에이전트를 구축하기 위한 라이브러리입니다.

기존 LangChain이 LLM과 외부 도구를 순차적으로 연결하는 체이닝(Chaining)에 초점을 두었다면, LangGraph는 이러한 연결 구조를 순환(Cycle)을 포함하는 그래프 형태로 확장해 더 유연하고 정교한 실행 흐름을 구성할 수 있습니다.

단순한 체인으로는 복잡해지기 쉬운 사용자 입력 재확인, 특정 조건이 만족될 때까지 작업 반복 등의 로직도 Node와 Edge로 표현할 수 있습니다.

※ 이 내용은 첨부 이미지의 설명 텍스트를 바탕으로 정리한 것이며, 이미지 자체는 삽입하지 않았습니다.

실전 상황: 쇼핑몰 고객센터 Agent

“배송비가 얼마야?”는 정책 문서를 검색하고, “내 주문 보여줘”는 DB를 조회하며, “주문을 취소해줘”는 실제 API를 호출해야 합니다.

문제: 요청마다 실행 경로가 다르고, 주문 취소 전에는 사용자 확인도 필요합니다.

LangGraph를 사용하면 요청 분류 → 적절한 작업 Graph 선택 → 승인 → 실행 → 결과 응답의 흐름을 명시적으로 관리할 수 있습니다.
판단 기준 단순한 1회성 호출이면 LangChain만으로 충분할 수 있습니다. 실행 흐름이 복잡해지면 LangGraph를 고려합니다.

Node는 State 일부를 갱신하고 Edge가 다음 단계를 결정합니다.
① Node와 Edge — 요청에 따라 경로가 바뀌는 Graph노드 = 작업 · 화살표 = Edge · 다이아몬드 = 조건

Edge는 항상 다음 Node를 지정하며, 조건부 Edge는 State에 따라 다른 경로를 선택합니다.

State

작업 메모리

질문, 사용자 ID, 분류 결과, 검색 문서, 재시도 횟수처럼 Graph가 공유하는 데이터입니다.

실전: “현재 주문 취소 승인 여부”를 다음 Node가 읽어야 한다면 State에 둡니다.

Node

작업 단위

LLM 호출, DB 조회, 문서 검색, API 실행 등 하나의 책임을 가진 함수입니다.

실전: classify_request, search_policy, cancel_order.

Edge

실행 규칙

다음에 어떤 Node를 실행할지 결정합니다. 고정 이동과 조건부 분기를 지원합니다.

실전: 분류 결과가 QUERY면 SQL Graph, ACTION이면 도구 실행 Graph로 이동.

Graph

전체 워크플로우

State·Node·Edge를 묶은 실행 단위입니다. 복잡한 흐름은 서브그래프로 나눌 수 있습니다.

실전 상황: 고객 요청 분기

message→분류 Node→QUERY→SQL Graph
message→분류 Node→ACTION→API 실행 Graph

실행 핵심 compile()은 그래프 실행 객체를 만들고, invoke()는 State를 입력해 그래프를 실행합니다. 위 콘솔은 단계별 개념을 보여주는 브라우저 시뮬레이션입니다.
② 기본 그래프 — 실행 순서 한눈에 보기노드 = 작업 · 화살표 = Edge · 다이아몬드 = 조건

START → classify → answer → END. Node 내부에서 State를 읽고 일부 필드를 갱신합니다.

  1. State 정의 — Graph에서 사용할 데이터를 정합니다.
  2. Node 작성 — 각 단계의 작업 함수를 만듭니다.
  3. Edge 연결 — 실행 순서와 분기 규칙을 정합니다.
  4. Compile — 실행 가능한 Graph로 완성합니다.
  5. Invoke — 초기 State를 넣어 실행합니다.
# pip install -U langgraph
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    message: str
    intent: str
    answer: str

def classify_node(state: AgentState):
    return {"intent": "POLICY" if "배송" in state["message"] else "OTHER"}

def answer_node(state: AgentState):
    return {"answer": "배송 정책을 확인해 주세요." if state["intent"] == "POLICY" else "상담원에게 문의해 주세요."}

graph = StateGraph(AgentState)
graph.add_node("classify", classify_node)
graph.add_node("answer", answer_node)
graph.add_edge(START, "classify")
graph.add_edge("classify", "answer")
graph.add_edge("answer", END)

app = graph.compile()
result = app.invoke({"message": "배송비가 얼마야?", "intent": "", "answer": ""})
print(result["answer"])
# 예제는 라우팅 구조 학습용이며 실제 정책 검색/RAG는 하지 않습니다.

실전 상황: 검색 결과가 없을 때

검색 Node가 문서를 찾지 못하면 바로 답변하지 않고 질문을 다시 작성한 뒤 재검색해야 합니다.

검색→문서 있음?→ 예답변
문서 없음→질문 재작성→재검색

이처럼 반복 루프와 종료 조건이 생기면 Graph로 표현하는 편이 안전합니다.

조건부 분기

언제 필요한가?

사용자 요청 유형이나 처리 결과에 따라 다음 작업이 달라질 때 필요합니다.

실전 예: “주문 내역 보여줘”는 SQL 조회, “주문 취소해줘”는 API 실행, “배송비가 얼마야?”는 정책 검색으로 분기합니다.

서브그래프

언제 필요한가?

하나의 Graph 안에 SQL 처리, API 처리, 문서 검색처럼 복잡한 흐름이 여러 개 들어갈 때 필요합니다.

실전 예: 메인 Graph는 요청을 분류하고, query_graph와 action_graph가 각자의 검증·재시도 흐름을 담당합니다.

Checkpointer

언제 필요한가?

작업이 길거나, 중단 후 재개해야 하거나, 장애가 발생해도 진행 상태를 복구해야 할 때 필요합니다.

실전 예:영속 저장소 기반 Checkpointer를 쓰면 서버 재시작 후에도 저장된 실행 상태를 복구할 수 있습니다. MemorySaver만 사용하면 프로세스 재시작 시 상태가 사라집니다.thread_id가 필요합니다.

Human-in-the-loop

언제 필요한가?

자동 실행하면 위험하거나 비용이 큰 작업에 사람의 승인이 필요할 때 사용합니다.

실전 예: 환불, 주문 취소, 계정 삭제, 개인정보 공개 직전에 interrupt()로 멈추고 승인 후 Command(resume=...)로 재개합니다.

병렬 실행과 Reducer

언제 필요한가?

서로 독립적인 작업을 동시에 실행해 응답 시간을 줄이고, 결과를 하나로 합쳐야 할 때 필요합니다.

실전 예:벡터 검색과 BM25 검색을 동시에 실행합니다. Reducer는 병렬 결과를 모으는 규칙이며, 중복 제거·점수 정규화·재랭킹은 별도 후처리로 구현합니다.

Streaming과 Retry

언제 필요한가?

응답이 오래 걸리거나 일시적인 네트워크·LLM 오류가 발생할 때 사용합니다.

실전 예: 여러 도구를 순서대로 실행하는 Agent의 진행 상황을 실시간으로 보여주고, 타임아웃이 난 호출만 재시도합니다.

5. RAG에서 LangGraph를 사용하는 실전 상황

③ Corrective RAG — 조건부 분기와 재검색 루프노드 = 작업 · 화살표 = Edge · 다이아몬드 = 조건

근거가 충분하면 답변, 부족하면 재작성 후 검색으로 복귀합니다. 최대 재검색 횟수를 넘으면 보류로 종료해야 합니다.

기본 RAG는 검색 후 답변을 생성합니다. LangGraph는 검색 결과 평가, 재검색, 멀티홉, 병렬 검색, 승인·복구처럼 실행 경로가 달라지는 RAG를 제어합니다.

① 별빛 2박3일 상품 자료 검색 숙소: 파도소리 리조트

실전 3 · Hybrid RAG: 병렬 검색과 결과 결합

질문→Vector 검색 ∥ BM25 검색→Reducer로 수집→중복 제거·재랭킹→LLM

동시에 끝난 두 검색 결과를 같은 State 키에 쓰려면 Annotated Reducer(예: operator.add)를 선언하거나 각 결과를 별도 키로 받습니다. Reducer는 합치는 방식만 정하며 중복 제거·순위 결합을 자동 수행하지 않습니다.

실전 4 · 최소 실행 예제 (외부 LLM·벡터 DB 없이)

실제 Python에서 실행할 수 있는 간이 Corrective RAG 그래프입니다. 두 번째 검색에서 관련 문서를 찾도록 만든 실습용 데이터입니다.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class RAGState(TypedDict):
    question: str
    query: str
    docs: list[str]
    retries: int
    answer: str

def retrieve(s: RAGState):
    docs = (["제주 냉장식품 항공편 취소 지연: 품질 확인 후 보상 여부 심사"]
            if "냉장식품" in s["query"] and "항공편" in s["query"]
            else ["일반 배송은 2~3일 소요"])
    return {"docs": docs}

def grade(s: RAGState):
    # 예제 판정: 실제 서비스에서는 관련성·충분성 평가 함수로 대체
    ok = any("품질 확인" in d for d in s["docs"])
    if ok: return "generate"
    if s["retries"] >= 1: return "no_evidence"
    return "rewrite"

def rewrite(s: RAGState):
    return {"query": "제주 냉장식품 항공편 취소 보상", "retries": s["retries"] + 1}

def generate(s: RAGState):
    return {"answer": "근거: " + s["docs"][0] + " / 보상 여부는 품질 확인 후 심사"}

def no_evidence(s: RAGState):
    return {"answer": "충분한 근거를 찾지 못했습니다."}

g = StateGraph(RAGState)
g.add_node("retrieve", retrieve)
g.add_node("rewrite", rewrite)
g.add_node("generate", generate)
g.add_node("no_evidence", no_evidence)
g.add_edge(START, "retrieve")
g.add_conditional_edges("retrieve", grade,
    {"rewrite": "rewrite", "generate": "generate", "no_evidence": "no_evidence"})
g.add_edge("rewrite", "retrieve")
g.add_edge("generate", END)
g.add_edge("no_evidence", END)
app = g.compile()
result = app.invoke({"question": "제주 지연 보상?", "query": "배송 보상",
                     "docs": [], "retries": 0, "answer": ""})
print(result["answer"])
주의: 위 grade는 조건부 Edge의 라우팅 함수이며 별도 Node가 아닙니다. 검색·평가를 독립 Node로 나누려면 add_node("grade", ...) 후 연결하세요. 실제 RAG에는 데이터 조회, 청킹·임베딩, 충분성 평가, LLM 생성 과정이 추가됩니다.
