1HITL 설계 이슈MCP·에이전트

interrupt가 하는 일

interrupt(값)을 만나면 그래프는 그 자리에서 멈추고, State를 체크포인터에 저장한 뒤 값을 사람(화면)에게 돌려줍니다. 사람이 Command(resume=답)으로 다시 invoke하면, 멈췄던 노드가 처음부터 다시 실행되고 이번에는 interrupt()가 답을 돌려줍니다.

노드 실행→interrupt(질문)→멈춤 · 저장→사람이 결정→Command(resume=답)→노드 처음부터 · interrupt()가 답을 반환

설계할 때 던질 5가지 질문

Q1. 어디서 멈출까?
되돌릴 수 없는 작업(메일, 삭제, 결제), 비용이 큰 작업, 규정상 승인이 필요한 작업 바로 앞. 모든 도구에서 멈추면 아무도 안 쓰는 시스템이 됩니다(검색은 자동).
Q2. 사람에게 무엇을 보여 줄까?
무엇을(도구 이름), 어떻게(인자), 왜(이유), 무엇을 고를 수 있는지(options). 값은 JSON으로 저장 가능해야 합니다(dict, list, str, 숫자).
Q3. 사람이 고를 수 있는 결정과 그 다음 길은?
approve → 실행 노드, reject → 실행 건너뛰기, edit → 고친 값으로 실행, escalate → 상급자. 결정마다 다음 노드를 Command(goto=...)로 정합니다.
Q4. 거부·수정 뒤에도 기록이 맞는가?
LLM이 도구를 부른 AIMessage에는 tool_call마다 ToolMessage 답이 있어야 합니다. 거부면 "거부됨" ToolMessage를 넣고 도구 노드를 건너뛰고, 수정이면 같은 id의 AIMessage로 교체합니다(01 add_messages).
Q5. 멈춘 동안 안전한가?
체크포인터 + thread_id 필수(04). 재개하면 노드가 처음부터 다시 돌기 때문에 interrupt 앞에 알림 발송 같은 부작용을 두지 않습니다(04 M7).

2리듀서와 병렬 실행RAGLangGraph 필수교재에 없음

병렬 실행은 "단계(super-step)" 단위로 일어난다

LangGraph는 그래프를 단계별로 실행합니다. 한 단계에서 실행할 수 있는 노드는 모두 동시에 실행되고, 단계가 끝나면 각 노드가 돌려준 값을 리듀서로 한꺼번에 State에 합칩니다. 그 다음 단계의 노드는 합쳐진 State를 봅니다.

단계 1: vector · bm25 · web 동시 실행 (셋 다 같은 State를 봄)→리듀서로 합치기→단계 2: answer (합쳐진 State를 봄)
['bm25(본 로그 0개)', 'vector(본 로그 0개)', 'web(본 로그 0개)', 'merge(본 로그 3개)']
# 같은 단계의 세 노드는 서로의 결과를 못 보고, 다음 단계 merge 는 셋을 다 본다

병렬 설계 5가지 질문

P1. 같은 키에 동시에 쓰나? → 그 키에는 리듀서 필수. 없으면 InvalidUpdateError (01).
P2. 결과 순서가 중요한가? → 병렬 결과의 순서는 정해져 있지 않습니다. 순서가 필요하면 리듀서 안에서 정렬합니다.
P3. 어디서 합류하나? 모두 기다리나? → add_edge(["a", "b"], "c")는 둘 다 끝나면 c를 한 번. add_edge("a","c") + add_edge("b","c")는 도착할 때마다 c를 실행합니다. 갈래 길이가 다르면 c가 두 번 돕니다. → M6
P4. 하나가 실패하면? → 그 단계 전체가 에러로 멈춥니다. 체크포인터가 있으면 성공한 노드의 결과는 보존되고, invoke(None, cfg)로 실패한 노드만 다시 실행합니다. 일시적 오류는 RetryPolicy로 자동 재시도. → M7
P5. 너무 많이 동시에 돌지 않나? → Send로 문서 100개를 보내면 LLM 100번이 동시에 갑니다. {"max_concurrency": 5}로 동시 실행 수를 제한합니다(API 속도 제한 대응).

병렬 + HITL: 여러 곳에서 동시에 멈추면

병렬 노드 두 개가 모두 interrupt하면 멈춤이 두 개 생깁니다. 이때 Command(resume="승인") 하나로는 재개할 수 없고, interrupt id별로 답을 줘야 합니다.

RuntimeError: When there are multiple pending interrupts, you must specify the interrupt id when resuming.
ints = result["__interrupt__"]                              # 두 개
answers = {i.id: ("승인" if i.value["who"] == "법무" else "보류") for i in ints}
app.invoke(Command(resume=answers), cfg)                    # id → 답 dict

def review(state) -> Command[Literal["tools", "reasoning"]]:
    ai = state["messages"][-1]; tc = ai.tool_calls[0]
    d = interrupt({"tool": tc["name"], "args": tc["args"]})
    if d["type"] == "approve":
        return Command(goto="tools")
    if d["type"] == "edit":                                   # 같은 id 로 교체 (add_messages)
        edited = AIMessage(content=ai.content, id=ai.id, tool_calls=[{**tc, "args": {**tc["args"], **d["args"]}}])
        return Command(goto="tools", update={"messages": [edited]})
    return Command(goto="reasoning",                           # 거부: tools 건너뛰기
                   update={"messages": [ToolMessage(content="사람이 거부", tool_call_id=tc["id"])]})

4실제예 ① 공유 폴더 파일 삭제 승인LangGraph 필수MCP·에이전트

STEP 1 · 상황 읽기

파일 정리 에이전트가 90일 이상 안 쓴 파일을 지우려 합니다. 삭제는 되돌릴 수 없으므로 담당자 승인 뒤에만 실행합니다.

STEP 2 · 설계 (Q1~Q5)
질문답
Q1 어디서 멈추나delete 노드 직전 (approve_gate)
Q2 무엇을 보여 주나action, path, reason, options
Q3 결정과 다음 길approve → delete, reject → cancel (status 기록)
Q5 안전InMemorySaver + 파일마다 thread_id. interrupt 앞에는 부작용 없음
plan→approve_gate (interrupt)→delete/cancel
STEP 3 · 코드
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

class DeleteState(TypedDict):
    path: str
    reason: str
    status: str

DELETED = []
def plan(s): return {"reason": f"{s['path']}는 90일 이상 사용되지 않음"}

def approve_gate(s) -> Command[Literal["delete", "cancel"]]:
    answer = interrupt({"action": "delete_file", "path": s["path"], "reason": s["reason"],
                        "options": ["approve", "reject"]})
    if answer == "approve":
        return Command(goto="delete")
    return Command(goto="cancel", update={"status": "취소: 사람이 거부"})

def delete(s):
    DELETED.append(s["path"])                 # 실제로는 os.remove
    return {"status": f"삭제 완료: {s['path']}"}
def cancel(s): return {}

g = StateGraph(DeleteState)
for n, f in [("plan", plan), ("approve_gate", approve_gate), ("delete", delete), ("cancel", cancel)]:
    g.add_node(n, f)
g.add_edge(START, "plan"); g.add_edge("plan", "approve_gate")
g.add_edge("delete", END); g.add_edge("cancel", END)
app = g.compile(checkpointer=InMemorySaver())
STEP 4 · 멈추고, 확인하고, 재개
cfg = {"configurable": {"thread_id": "del-1"}}
r = app.invoke({"path": "/share/old_report.xlsx"}, cfg)
print("멈춤:", r["__interrupt__"][0].value)
st = app.get_state(cfg)
print("next:", st.next, "| 대기 중 interrupt:", st.interrupts[0].value["path"])
print("재개:", app.invoke(Command(resume="approve"), cfg)["status"], "| DELETED:", DELETED)

cfg2 = {"configurable": {"thread_id": "del-2"}}
app.invoke({"path": "/share/contract.pdf"}, cfg2)
print("거부:", app.invoke(Command(resume="reject"), cfg2)["status"], "| DELETED:", DELETED)

  3. 파일마다 thread_id. 여러 삭제 요청이 서로의 승인과 섞이지 않습니다.

from typing import Annotated
from operator import add

def merge_sorted(old, new):
    best = {d["id"]: d for d in (old or [])}
    for d in new or []:
        if d["id"] not in best or d["score"] > best[d["id"]]["score"]:
            best[d["id"]] = d
    return sorted(best.values(), key=lambda d: -d["score"])

class SearchState(TypedDict):
    question: str
    docs: Annotated[list[dict], merge_sorted]
    trace: Annotated[list[str], add]
    answer: str

from langchain_core.tools import tool

SENT = []

def reasoning(state: MessagesState):           # 가짜 LLM: 첫 요청엔 send_email 호출
    last = state["messages"][-1]
    if isinstance(last, HumanMessage):
        return {"messages": [AIMessage(content="", tool_calls=[{"name": "send_email",
                "args": {"to": "hello@test.com", "subject": "회의", "body": "내일 2시"}, "id": "call_1"}])]}
    return {"messages": [AIMessage(content=f"완료: {last.content}")]}

def check_sensitive_tools(state):               # 위키독스 2-4-1 그대로
    last = state["messages"][-1]
    if not getattr(last, "tool_calls", None):
        return {}
    for tc in last.tool_calls:
        if tc["name"] in {"send_email"}:
            r = interrupt({"tool": tc["name"], "args": tc["args"]})
            if r != "approve":
                return {"messages": [ToolMessage(content=f"사용자가 '{tc['name']}' 실행을 거부했습니다.",
                                                 tool_call_id=tc["id"])]}
    return {}

    return "check_sensitive" if getattr(state["messages"][-1], "tool_calls", None) else END

g.add_node("tools", ToolNode([send_email]))

def review(s: MessagesState) -> Command[Literal["tools", "reasoning"]]:
    ai = s["messages"][-1]
    tc = ai.tool_calls[0]

# ② 병렬 + 리듀서에서 중복 제거
def dedup(old, new):
    seen = {d.replace("web:", "") for d in old or []}
    return (old or []) + [d for d in new or [] if d.replace("web:", "") not in seen]

    calls["vector"] += 1; return {"docs": ["vector결과"]}
def web(s):
    calls["web"] += 1
    if fail["on"]:
        raise ConnectionError("웹검색 API 타임아웃")
    return {"docs": ["web결과"]}

g = StateGraph(S); g.add_node("vector", vector); g.add_node("web", web)
g.add_edge(START, "vector"); g.add_edge(START, "web")
STEP 2 · 방법 ①: 체크포인터로 실패한 것만 다시
app = g.compile(checkpointer=InMemorySaver()); cfg = {"configurable": {"thread_id": "f"}}
try:
    app.invoke({"docs": []}, cfg)
except ConnectionError as e:
    print("실패:", e, "| next:", app.get_state(cfg).next)
fail["on"] = False                     # API 복구
print(app.invoke(None, cfg), calls)
실제 출력
실패: 웹검색 API 타임아웃 | next: ('web',)
{'docs': ['vector결과', 'web결과']} {'vector': 1, 'web': 2}

vector는 한 번만 실행됐습니다. 성공한 노드의 결과는 체크포인트에 "대기 중 쓰기"로 보존되고, invoke(None)은 실패한 web만 다시 실행합니다.

STEP 3 · 방법 ②: RetryPolicy로 자동 재시도

web 노드가 처음 두 번은 실패하고 세 번째에 성공한다고 할 때, 노드 등록만 바꿔 자동으로 재시도하게 하세요.

예시 답안 보기

g.add_node("web", web, retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.5,
                                                retry_on=ConnectionError))
{'docs': ['web결과']} {'web': 3}       # 두 번 실패 후 세 번째 성공, 에러 없이 끝남
STEP 4 · 설계 판단

RetryPolicy와 체크포인터 재개는 각각 언제 쓰나요? 웹 검색이 3번 다 실패하면 답변을 아예 못 하게 둘까요?

확인

RetryPolicy: 몇 초 안에 풀리는 일시적 오류. 체크포인터 재개: 오래 걸리는 장애나 사람이 고친 뒤 다시 돌릴 때. 웹 검색은 "있으면 좋은" 결과이므로, 재시도 후에도 실패하면 노드 안에서 예외를 잡아 {"docs": []}를 돌려주고 벡터 결과만으로 답하는 것이 사용자 경험에 낫습니다(우아한 실패).

STEP 5 · 확인
★★★ 도전LangGraph 필수MCP·에이전트

M8. 계약서를 법무·재무가 동시에 검토하고 승인

STEP 1 · 상황 읽기

계약서 검토를 법무팀과 재무팀이 동시에 합니다. 각 팀 노드가 담당자에게 의견을 묻고(interrupt), 두 의견이 모두 모이면 최종 판정 노드가 "둘 다 승인이면 체결, 아니면 보류"를 정합니다.

START→legal (interrupt)+finance (interrupt)→decide→END
STEP 2 · 설계 (P1, P3, Q2)

두 노드가 의견을 쓰는 키와 리듀서, 합류 방법, interrupt 값(담당자 화면에 보여 줄 것)을 정하세요.

확인

reviews: Annotated[list[str], add] (동시 쓰기), add_edge(["legal", "finance"], "decide"), interrupt 값은 {"who": "법무", "doc": ...}처럼 누가 답해야 하는지 포함.

STEP 3 · 그래프 작성
예시 답안 보기
class Contract(TypedDict):
    doc: str
    reviews: Annotated[list[str], add]
    result: str

def legal(s):   return {"reviews": [f"법무:{interrupt({'who': '법무', 'doc': s['doc']})}"]}
def finance(s): return {"reviews": [f"재무:{interrupt({'who': '재무', 'doc': s['doc']})}"]}
def decide(s):
    ok = all(r.endswith("승인") for r in s["reviews"])
    return {"result": "체결" if ok else "보류"}

g = StateGraph(Contract)
for n, f in [("legal", legal), ("finance", finance), ("decide", decide)]:
    g.add_node(n, f)
g.add_edge(START, "legal"); g.add_edge(START, "finance")
g.add_edge(["legal", "finance"], "decide"); g.add_edge("decide", END)
app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "contract-A"}}
r = app.invoke({"doc": "계약서A", "reviews": [], "result": ""}, cfg)
STEP 4 · 멈춤이 두 개일 때 재개

먼저 app.invoke(Command(resume="승인"), cfg)을 해 보고 에러를 확인한 뒤, interrupt id별로 답하세요(법무 승인, 재무 보류).

예시 답안 보기
RuntimeError: When there are multiple pending interrupts, you must specify the interrupt id when resuming.
ints = r["__interrupt__"]
print([i.value for i in ints])
answers = {i.id: ("승인" if i.value["who"] == "법무" else "보류") for i in ints}
print(app.invoke(Command(resume=answers), cfg))
[{'who': '재무', 'doc': '계약서A'}, {'who': '법무', 'doc': '계약서A'}]
{'doc': '계약서A', 'reviews': ['재무:보류', '법무:승인'], 'result': '보류'}

interrupt 목록과 reviews의 순서는 실행마다 다를 수 있습니다. 그래서 순서가 아니라 value["who"]로 구분합니다.
