학습 목표
  • 어떤 값을 State, RunnableConfig, context 중 어디에 둘지 이유를 들어 고른다. 교재에 없음
  • 체크포인터와 thread_id로 사용자·세션별 대화 기억을 설계한다.
  • 개발용(InMemorySaver)과 영구 저장(SqliteSaver)을 바꿔 끼우고, 프로세스를 다시 시작해도 기억이 남는 것을 확인한다.
  • Time Travel로 과거 지점에서 상태를 고쳐 다시 실행하고, interrupt 재개 때 값이 바뀌지 않게 만든다.

RAG대화형 RAG는 이전 질문을 기억해야 "그거 이월도 돼?" 같은 후속 질문을 처리합니다. Time Travel로 검색어만 고쳐 다시 돌려 볼 수 있습니다.
LangGraph 필수체크포인터가 있어야 interrupt(HITL), Time Travel, 장애 후 재개가 가능합니다.
MCP·에이전트사용자 정보·DB 연결·API 키를 State에 넣으면 체크포인터 저장소에 그대로 기록됩니다. 어디에 둘지가 보안 문제입니다.

1State vs RunnableConfigLangGraph 필수교재에 없음

한 문장 정리

State는 그래프가 일하면서 만들고 바꾸고 기억하는 데이터, RunnableConfig는 이번 실행을 어떻게 돌릴지 알려 주는 설정입니다. State는 체크포인터에 저장되고, config는 저장되지 않습니다.

비유: 병원 진료

병원에서LangGraph에서
State진료 차트. 의사들이 돌아가며 적고, 다음 진료 때 다시 꺼내 본다.노드가 읽고 쓰는 dict. 체크포인터가 보관하고, 같은 thread_id로 오면 이어서 쓴다.
RunnableConfig접수증. "누구 차트인지(환자번호)", "오늘은 어떤 진료 방식으로". 진료가 끝나면 버린다.thread_id, recursion_limit, 이번만 쓸 옵션(model 등). 이번 invoke에만 쓰이고 저장되지 않는다.
context (런타임 컨텍스트)신분증·보험 정보. 진료 내내 같고, 차트에 옮겨 적지 않는다.context=UserCtx(...)로 전달. 실행 내내 고정, 노드는 읽기만, 저장되지 않는다. (LangGraph 0.6+ 권장 방식)

어디에 둘지 고르는 4가지 질문

Q1. 노드가 이 값을 바꾸나? → 바꾸면 State. config와 context는 읽기 전용입니다.
Q2. 다음 턴(다음 invoke)에도 기억해야 하나? → 그렇다면 State. config에 넣으면 다음 호출 때 사라집니다.
Q3. "이번 실행을 어떻게"에 관한 것인가? → 어느 대화인지(thread_id), 실행 한도, 이번만 바꿀 옵션이면 config.
Q4. 실행 내내 고정이고, 저장되면 안 되는가? → 사용자 신원, DB 연결, API 클라이언트·키는 context(또는 config). State에 넣으면 저장소에 기록되거나 직렬화 에러가 납니다.

위키독스와의 연결 1-3-3-4는 모델 이름 등을 config["configurable"]로, 1-4는 user_id를 Runtime[Context]로 넘깁니다. 둘 다 동작합니다. 새 코드는 "실행 옵션 = config, 고정 사용자 정보·자원 = context"로 나누면 깔끔합니다.

2체크포인터 설계 이슈RAGMCP·에이전트

체크포인터가 하는 일

그래프의 단계(super-step)가 끝날 때마다 State 전체를 저장합니다. 저장 위치의 열쇠는 config의 thread_id입니다. 같은 thread_id로 다시 invoke하면 마지막 State에서 이어 갑니다.

invoke(입력, thread_id=A)→마지막 State 불러오기→입력과 합치기(리듀서)→노드 실행→단계마다 저장

설계할 때 던질 5가지 질문

Q1. 무엇을 기억해야 하나?
State가 곧 저장 내용입니다. 기억할 필요 없는 큰 데이터, 비밀 값, 연결 객체는 State에서 빼세요(1번 탭).
Q2. 누구 단위로 기억하나? (thread_id 설계)
"사용자 한 명 = 대화 하나"인지, "사용자 × 대화방"인지 정합니다. 예: f"{user_id}:{session_id}". 매번 새로 만들면 기억이 없고, 모두 같으면 서로 섞입니다.
Q3. 어디에 저장하나?
개발·테스트는 InMemorySaver(프로세스가 끝나면 사라짐), 서버 한 대는 SqliteSaver, 서버 여러 대는 PostgresSaver. 바꿔 끼워도 그래프 코드는 그대로입니다.
Q4. 되돌리거나 다시 실행할 일이 있나?
Time Travel(과거 지점에서 고쳐 다시 실행), interrupt 재개, 장애 후 재시작. 재개되면 노드는 처음부터 다시 실행되므로 랜덤·시간·LLM 호출은 @task로 감싸고, 메일 발송 같은 외부 작업은 두 번 해도 안전하게(멱등) 만듭니다.
Q5. 여러 대화에 걸쳐 기억해야 하나?
체크포인터는 대화(thread) 하나 안의 기억입니다. "이 사용자는 매운 음식을 좋아함"처럼 대화를 넘는 기억은 Store(장기 기억)에 둡니다.

@task
def new_order_no() -> str:
    return f"ORD-{random.randint(1000, 9999)}"

def create_order(state):

4실제예 ① 세션을 기억하는 사내 상담봇LangGraph 필수MCP·에이전트

STEP 1 · 상황 읽기

사내 상담봇이 같은 대화방 안에서는 이름을 기억해야 하고, 새 대화방에서는 처음부터 시작해야 합니다. 말투(공손/기본)는 요청마다 바꿀 수 있고, 부서 정보는 로그인 정보에서 옵니다.

STEP 2 · 어디에 둘지 설계
값판단위치

STEP 3 · 코드
from dataclasses import dataclass
from typing import Annotated
from operator import add
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.runtime import Runtime
from langchain_core.runnables import RunnableConfig
from langchain_core.messages import HumanMessage, AIMessage

@dataclass
class UserCtx:
    user_id: str
    dept: str

class ChatState(MessagesState):
    turn: Annotated[int, add]

def bot(state: ChatState, config: RunnableConfig, runtime: Runtime[UserCtx]):
    polite = config["configurable"].get("tone") == "공손"
    last = state["messages"][-1].content
    names = [m.content.split("내 이름은 ")[1].rstrip("야") for m in state["messages"]
             if isinstance(m, HumanMessage) and "내 이름은 " in m.content]
    if "이름" in last and "뭐" in last:
        if names:
            reply = f"{names[-1]}님이라고 하셨" + ("습니다." if polite else "어요.")
        else:
            reply = "아직 이름을 듣지 못했" + ("습니다." if polite else "어요.")
    else:
        reply = "반갑습니다!" if polite else "반가워요!"
    reply += f" ({runtime.context.dept} · {state['turn'] + 1}번째 턴)"
    return {"messages": [AIMessage(content=reply)], "turn": 1}

g = StateGraph(ChatState, context_schema=UserCtx)
g.add_node("bot", bot); g.add_edge(START, "bot"); g.add_edge("bot", END)
chat = g.compile(checkpointer=InMemorySaver())

  2. 대화방이 다르면 처음부터. session-2는 이름도 턴 수도 새로 시작합니다.
  3. 저장된 것은 State뿐. 체크포인트에는 messages와 turn만 있고 tone, user_id, dept는 없습니다.

"연차 이월 되나요?"라는 질문에 RAG가 엉뚱하게 "연차는 15일"이라고 답했습니다. 질문 전체를 다시 돌리지 않고, 검색어를 만든 지점으로 돌아가 검색어만 고쳐 그 뒤만 다시 실행하려 합니다.

make_query→retrieve→generate
STEP 2 · 그래프와 첫 실행
class RagState(TypedDict):
    question: str
    query: str
    docs: list[str]
    answer: str

INDEX = {"연차": "연차는 15일", "연차 이월": "연차는 최대 5일까지 다음 해로 이월"}
def make_query(s): return {"query": s["question"].split()[0]}          # 첫 단어만 → 버그
def retrieve(s):   return {"docs": [v for k, v in INDEX.items() if k == s["query"]]}
def generate(s):   return {"answer": " / ".join(s["docs"]) or "근거 없음"}

b = StateGraph(RagState)
for n, f in [("make_query", make_query), ("retrieve", retrieve), ("generate", generate)]:
    b.add_node(n, f)
b.add_edge(START, "make_query"); b.add_edge("make_query", "retrieve")
b.add_edge("retrieve", "generate"); b.add_edge("generate", END)
rag = b.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "rag-1"}}
print("1차:", rag.invoke({"question": "연차 이월 되나요?"}, cfg)["answer"])
1차: 연차는 15일
STEP 3 · 기록 보기: 어디서 틀렸나
for s in rag.get_state_history(cfg):
    print("step", s.metadata["step"], "next", s.next, "query=", s.values.get("query"))
step 3 next () query= 연차
step 2 next ('generate',) query= 연차
step 1 next ('retrieve',) query= 연차          ← make_query 직후. 여기서 고친다
step 0 next ('make_query',) query= None
step -1 next ('__start__',) query= None
STEP 4 · 고쳐서 그 지점부터 다시 실행
target = next(s for s in rag.get_state_history(cfg) if s.next == ("retrieve",))
new_cfg = rag.update_state(target.config, {"query": "연차 이월"}, as_node="make_query")
print("2차:", rag.invoke(None, new_cfg)["answer"])          # 반환된 new_cfg 사용

2차: 연차는 최대 5일까지 다음 해로 이월
최신 상태: 연차는 최대 5일까지 다음 해로 이월

  2. 고친 건 새 갈래(fork). 원래 기록은 지워지지 않고, 수정 지점에서 새 갈래가 생깁니다.
  3. 반환된 config로 실행. 위키독스처럼 target.config로 실행하면 수정 전 값으로 다시 돕니다 → M6

M6. 고쳤는데 결과가 그대로 (Time Travel)

STEP 1 · 상황 읽기

위키독스 1-4-3의 번역 검수 예제를 LLM 없이 옮겼습니다. 번역을 "부지런한 자가 성공한다."로 고쳐 다시 실행했는데 결과가 원래 번역 그대로입니다.

class T(TypedDict):
    original: str; translated: str; review: str; final_output: str

def translate(s): return {"translated": "일찍 일어나는 새가 벌레를 잡는다."}
def review(s):    return {"review": f"검수({s['translated']})"}
def finalize(s):  return {"final_output": f"번역: {s['translated']} / {s['review']}"}

b = StateGraph(T)
for n, f in [("translate", translate), ("review", review), ("finalize", finalize)]:
    b.add_node(n, f)
b.add_edge(START, "translate"); b.add_edge("translate", "review")
b.add_edge("review", "finalize"); b.add_edge("finalize", END)
graph = b.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "tt"}}
graph.invoke({"original": "The early bird catches the worm.", "translated": "", "review": "", "final_output": ""}, cfg)

target = next(s for s in graph.get_state_history(cfg) if s.next == ("review",))
graph.update_state(target.config, {"translated": "부지런한 자가 성공한다."}, as_node="translate")
print(graph.invoke(None, config=target.config)["final_output"])        # 위키독스 방식
STEP 2 · 결과 예측
실제 출력
번역: 일찍 일어나는 새가 벌레를 잡는다. / 검수(일찍 일어나는 새가 벌레를 잡는다.)
STEP 3 · 원인: config가 가리키는 곳

target.config 안의 checkpoint_id는 어느 체크포인트를 가리키나요? update_state는 기존 체크포인트를 고칠까요, 새로 만들까요?

확인

update_state는 기존 체크포인트를 고치지 않고 그 뒤에 새 체크포인트를 만들고, 그 config를 돌려줍니다. target.config는 여전히 수정 전 체크포인트를 가리키므로, 그것으로 실행하면 원래 값에서 다시 돕니다. Git으로 치면 "새 커밋을 만들고 옛 커밋을 체크아웃한" 셈입니다.

STEP 4 · 고치기

M7. 결재 후 주문번호가 바뀐다 (Durable Execution)

STEP 1 · 상황 읽기

구매 에이전트가 주문번호를 만들고 결재자에게 "주문번호 ORD-xxxx 결제할까요?"를 묻습니다. 결재자가 승인한 뒤 저장된 주문번호가 화면에서 본 번호와 다릅니다.

import random
from langgraph.types import interrupt, Command

class Order(TypedDict):
    item: str
    order_no: str
    approved: str

calls = {"n": 0}
def create_order(s):
    calls["n"] += 1
    order_no = f"ORD-{random.randint(1000, 9999)}"
    ok = interrupt(f"{s['item']} 주문번호 {order_no} 결제할까요?")
    return {"order_no": order_no, "approved": ok}

g = StateGraph(Order); g.add_node("create", create_order); g.add_edge(START, "create")
app = g.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "o1"}}
print("화면:", app.invoke({"item": "노트북"}, c)["__interrupt__"][0].value)
print("저장:", app.invoke(Command(resume="예"), c), "| 노드 실행 횟수:", calls["n"])
STEP 2 · 결과 예측

노드는 몇 번 실행될까요? 화면의 번호와 저장된 번호는 같을까요?

실제 출력 (번호는 매번 다름)
화면: 노트북 주문번호 ORD-7065 결제할까요?
저장: {'item': '노트북', 'order_no': 'ORD-5113', 'approved': '예'} | 노드 실행 횟수: 2
STEP 3 · 원인: 재개는 노드를 처음부터 다시 실행한다 (Q4)
확인

체크포인트는 노드 단위로 저장됩니다. interrupt로 멈춘 노드는 아직 끝나지 않았으므로, 재개하면 그 노드를 맨 처음부터 다시 실행합니다. interrupt는 두 번째에 resume 값을 돌려주지만, 그 앞의 random은 새로 실행되어 다른 번호가 나옵니다. LLM 호출, 현재 시각, uuid도 마찬가지입니다.

STEP 4 · 고치기 두 가지

방법 A: 비결정적 작업을 @task로 감싼다. 방법 B: 번호 생성과 결재를 다른 노드로 나눈다(앞 노드가 끝나면 State에 저장되므로).

예시 답안 보기 (방법 A)
from langgraph.func import task

@task
def new_order_no() -> str:
    return f"ORD-{random.randint(1000, 9999)}"

def create_order(s):
    order_no = new_order_no().result()         # 재개 때는 저장된 결과를 돌려줌
    ok = interrupt(f"{s['item']} 주문번호 {order_no} 결제할까요?")
    return {"order_no": order_no, "approved": ok}
화면: 노트북 주문번호 ORD-8377 결제할까요?
저장: {'item': '노트북', 'order_no': 'ORD-8377', 'approved': '예'} | 노드 실행: 2 | 번호 생성: 1
방법 B 힌트
# make_no 노드: return {"order_no": f"ORD-{random...}"}     → 끝나면 저장됨
# approve 노드: ok = interrupt(f"... {s['order_no']} ..."); return {"approved": ok}
# START → make_no → approve
STEP 5 · 확인과 토론
토론 예시

재개할 때 메일이 한 번 더 발송됩니다. 막는 방법: 메일 발송을 @task로 감싸 한 번만 실행되게 하거나, 별도 노드로 분리하거나, 주문번호를 키로 "이미 보냈으면 건너뛰기"(멱등)로 만듭니다. 위키독스 1-4-4의 upsert 예시와 같은 원리입니다.
