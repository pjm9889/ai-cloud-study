1스트리밍 설계 이슈RAGMCP·에이전트

스트리밍 = 결과를 기다리지 않고 "중간에" 받기

invoke()는 끝날 때까지 기다렸다가 최종 상태 하나를 줍니다. stream()은 실행되는 동안 일어나는 일을 하나씩 내보냅니다. 무엇을 내보낼지를 stream_mode로 고릅니다.

모드언제 나오나한 번에 나오는 것화면에서
values단계가 끝날 때마다전체 State대시보드 전체 다시 그리기
updates노드가 끝날 때마다{노드이름: 바뀐 값}"✔ 검색 완료" 같은 단계 표시
messagesLLM이 글자를 낼 때마다(청크, 메타데이터)답변이 글자 단위로 써지는 효과
custom노드가 writer()를 부를 때보낸 값 그대로진행률, "문서 3/10 처리"
debug모든 내부 사건{"type": "task" | "task_result" | "checkpoint", ...}개발 중 추적용

설계할 때 던질 5가지 질문

Q1. 누구에게 무엇을 보여 주나?
사용자에게는 진행 단계(updates/custom)와 답변 글자(messages). 운영자에게는 바뀐 값 기록(updates). 개발자에게는 debug. 대상마다 모드를 고르고 필요하면 리스트로 섞습니다.
Q2. 무엇을 걸러야 하나?
messages 스트림에는 모든 LLM 호출(질문 분류, 안전 판정, 답변)과 노드가 직접 만든 메시지가 섞입니다. 사용자에게 보일 LLM에 태그를 달고 그것만 출력합니다.
Q3. 어디서 나온 이벤트인가?
노드 이름은 metadata["langgraph_node"], 서브그래프는 subgraphs=True일 때 namespace로 구분합니다. subgraphs=True가 아니면 서브그래프 안의 custom 이벤트는 아예 오지 않습니다.
Q4. 받는 쪽 코드를 어떻게 단순하게 만들까?
모드를 여러 개 쓰면 출력 모양이 섞입니다. version="v2"로 받으면 모든 이벤트가 {"type", "ns", "data"} 같은 모양이라 한 루프에서 처리하기 쉽습니다.
Q5. 중간에 실패하거나 재시도하면 화면은?
이미 보낸 글자는 되돌릴 수 없습니다. 재시도가 일어나면 같은 글자가 다시 옵니다. 화면은 "시도 시작" 신호를 받으면 지우고 다시 쓰거나, 최종 updates를 기준으로 맞춥니다. → 2번 탭, M7

출력 모양 정리 (실행 확인)

app.stream(x, stream_mode="updates")                          # {'process': {...}}
app.stream(x, stream_mode=["values", "updates"])              # ('values', {...}) / ('updates', {...})
app.stream(x, stream_mode="updates", subgraphs=True)          # ((namespace...), {...})
app.stream(x, stream_mode=["updates", "custom"], version="v2")  # {'type': 'updates', 'ns': (), 'data': {...}}
[('values', {'message': 'Hello'}), ('updates', {'process': {'message': 'Processed: Hello'}}), ('values', {'message': 'Processed: Hello'})]

2재시도 RetryPolicyLangGraph 필수교재에 없음

왜 필요한가

LLM API와 외부 검색 API는 가끔 실패합니다. 연결 끊김, 서버 과부하(503), 속도 제한(429) 같은 오류는 잠시 뒤 다시 하면 대부분 성공합니다. 이런 일시적 오류마다 사용자에게 에러를 보여 주거나 처음부터 다시 실행하는 대신, 해당 노드만 자동으로 몇 번 더 시도하게 하는 것이 RetryPolicy입니다.

from langgraph.types import RetryPolicy

g.add_node("generate", generate,
           retry_policy=RetryPolicy(max_attempts=3))     # 노드마다 붙인다

설정값 (기본값은 실행으로 확인)

인자기본값뜻
max_attempts3첫 시도 포함 최대 횟수
initial_interval0.5초첫 재시도 전 대기
backoff_factor2.0재시도마다 대기 시간 배수 (0.5 → 1 → 2초)
max_interval128초대기 시간 상한
jitterTrue대기 시간에 무작위 값을 더해 여러 요청이 동시에 몰리지 않게
retry_ondefault_retry_on어떤 에러를 재시도할지 (예외 클래스, 튜플, 또는 판정 함수)

기본으로 재시도되는 에러 (실행 확인)

에러기본 재시도메모
ConnectionError예연결 끊김
HTTP 5xx (예: 503)예서버 쪽 일시 장애
HTTP 4xx (예: 400)아니오요청이 잘못됨. 다시 해도 실패
ValueError아니오코드·데이터 문제. LLM 출력 JSON 파싱 실패도 여기
파이썬 TimeoutError아니오뜻밖의 함정. 타임아웃을 재시도하려면 retry_on에 직접 넣어야 함 → M6

재시도 설계 질문

R1. 이 노드의 실패는 일시적인가?
네트워크·서버 오류면 재시도, 잘못된 입력·코드 버그면 재시도해도 같은 결과입니다(비용만 듦).
R2. 다시 실행해도 안전한가?
재시도는 노드를 처음부터 다시 실행합니다. 메일 발송, 결제처럼 부작용이 있는 노드는 멱등하게 만들거나 재시도하지 않습니다(04 M7과 같은 원리).
R3. 끝내 실패하면?
max_attempts를 다 쓰면 마지막 에러가 그대로 올라옵니다. "있으면 좋은" 단계(웹 검색)는 노드 안에서 잡아 빈 결과나 보조 모델로 넘어가게(fallback), 꼭 필요한 단계는 에러를 올려 체크포인터로 나중에 재개합니다(05 M7).
R4. 스트리밍 중이었다면?
실패 전에 보낸 custom 이벤트·LLM 글자는 이미 화면에 나갔습니다. 재시도하면 처음부터 다시 오므로 글자가 겹칩니다. → 실제예 ②, M7
재시도 1번 일어났을 때 화면에 이어 붙인 글자:  "연차는 15일연차는 15일입니다"
LLM 자체의 재시도와 차이 ChatOpenAI 같은 모델 객체에도 max_retries가 있습니다. 그것은 "API 호출 한 번"을 재시도하고, RetryPolicy는 "노드 전체"를 재시도합니다. 보통 모델 쪽은 짧게, 노드 쪽은 검색·파싱까지 포함한 단계 재시도에 씁니다. 둘 다 크게 잡으면 3 × 3 = 9번까지 호출될 수 있습니다.

4실제예 ① 사내 규정 RAG: 진행 상황 + 답변 글자RAGLangGraph 필수

STEP 3 · 그래프 (LLM은 가짜 모델로)
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.config import get_stream_writer
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import AIMessage, AIMessageChunk, HumanMessage

DOCS = {"연차": "연차는 입사 1년 후 15일", "이월": "연차는 최대 5일까지 이월"}

class RagState(MessagesState):
    docs: list[str]

def retrieve(s: RagState):
    w = get_stream_writer()
    q = s["messages"][-1].content
    found = []
    for i, (k, v) in enumerate(DOCS.items(), 1):
        w({"stage": "retrieve", "msg": f"문서 {i}/{len(DOCS)} 확인"})
        if k in q:
            found.append(v)
    w({"stage": "retrieve", "msg": f"{len(found)}건 찾음"})
    return {"docs": found}

answer_llm = GenericFakeChatModel(messages=iter([AIMessage(content="연차는 15일이고 최대 5일까지 이월됩니다.")]))

def generate(s: RagState):
    get_stream_writer()({"stage": "generate", "msg": "답변 작성 중"})
    return {"messages": [answer_llm.invoke(s["messages"], config={"tags": ["answer"]})]}

g = StateGraph(RagState)
g.add_node("retrieve", retrieve); g.add_node("generate", generate)
g.add_edge(START, "retrieve"); g.add_edge("retrieve", "generate"); g.add_edge("generate", END)
rag = g.compile()
STEP 4 · 세 모드를 한 루프에서
for mode, data in rag.stream({"messages": [HumanMessage(content="연차 이월 되나요?")]},
                             stream_mode=["updates", "custom", "messages"]):
    if mode == "custom":
        print(f"  [{data['stage']}] {data['msg']}")
    elif mode == "messages":
        chunk, md = data
        if isinstance(chunk, AIMessageChunk) and "answer" in md.get("tags", []):
            print(f"  토큰:{chunk.content!r}")
    elif mode == "updates":
        print(f"✔ {list(data)[0]} 완료")

5실제예 ② LLM 연결이 끊겼다 다시 붙을 때LangGraph 필수MCP·에이전트

STEP 1 · 상황 읽기

답변 노드가 글자를 보내던 중 LLM 연결이 끊깁니다. RetryPolicy 덕분에 두 번째 시도에서 성공하지만, 화면에는 앞부분이 두 번 찍혔습니다.

STEP 2 · 재현
from typing_extensions import TypedDict
from langgraph.types import RetryPolicy

def make_gen(attempt_event):
    calls = {"n": 0}
    def gen(s):
        calls["n"] += 1
        w = get_stream_writer()
        if attempt_event:
            w({"type": "attempt", "n": calls["n"]})          # 시도 시작 신호
        for tok in ["연차는", " 15일", "입니다"]:
            w({"type": "token", "text": tok})
            if calls["n"] == 1 and tok == " 15일":
                raise ConnectionError("LLM 연결 끊김")     # 첫 시도는 중간에 실패
        return {"answer": "연차는 15일입니다"}
    return gen

class T(TypedDict):
    answer: str

def build(attempt_event):
    g = StateGraph(T)
    g.add_node("gen", make_gen(attempt_event),
               retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.01, retry_on=ConnectionError))
    g.add_edge(START, "gen")
    return g.compile()

screen = ""
for mode, d in build(False).stream({"answer": ""}, stream_mode=["custom", "updates"]):
    if mode == "custom":
        screen += d["text"]
print("화면:", screen)

    for i, f in enumerate(s["files"], 1):
        out.append(f"{f} 요약")                       # 실제로는 LLM 호출
        w({"current": i, "total": len(s["files"]), "file": f})

g = StateGraph(Batch); g.add_node("summ", summarize_all); g.add_edge(START, "summ")

    print(f"  [{bar}] {p['current']}/{p['total']} {p['file']}")

M6. 어떤 에러를 재시도할까

STEP 1 · 상황 읽기

LLM 노드에 기본 RetryPolicy를 붙였습니다. 그런데 "응답 시간 초과"는 재시도 없이 바로 사용자에게 에러가 보이고, "JSON 파싱 실패"도 재시도되지 않습니다.

class P(TypedDict):
    answer: str
    used: str

def flaky_factory(errors):                 # 주어진 에러를 차례로 던진 뒤 성공
    seq = list(errors)
    def node(s):
        if seq:
            raise seq.pop(0)
        return {"answer": "정상 응답", "used": "primary"}
    return node

def run_policy(errors, policy):
    g = StateGraph(P); g.add_node("llm", flaky_factory(errors), retry_policy=policy); g.add_edge(START, "llm")
    try:
        return g.compile().invoke({"answer": "", "used": ""})
    except Exception as e:
        return f"{type(e).__name__}: {e}"
STEP 2 · 예측 (R1)

run_policy([ConnectionError("x"), ConnectionError("x")], RetryPolicy(initial_interval=0.01))
run_policy([TimeoutError("응답 시간 초과")], RetryPolicy(initial_interval=0.01))
run_policy([TimeoutError("t")], RetryPolicy(initial_interval=0.01, retry_on=(ConnectionError, TimeoutError)))
run_policy([ConnectionError("x")] * 4, RetryPolicy(initial_interval=0.01))

        return {"answer": "보조 모델 응답", "used": "fallback"}

RetryPolicy와 함께 쓰면 "재시도 → 그래도 실패하면 보조"가 됩니다. 단, 노드 안에서 에러를 잡으면 RetryPolicy는 에러를 보지 못해 재시도하지 않으니, 재시도할 부분과 fallback 부분을 노드로 나누거나 순서를 정해야 합니다.

STEP 1 · 상황 읽기

실제예 ②는 custom 이벤트로 흉내 냈습니다. 이번엔 messages 모드(실제 LLM 글자 스트림)에서 같은 일이 생기는지 확인하고 고칩니다.

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel

calls = {"n": 0}
def gen(s):
    calls["n"] += 1
    llm = GenericFakeChatModel(messages=iter([AIMessage(content="연차는 15일 입니다")]))
    if calls["n"] == 1:                              # 첫 시도: 글자 두 개 보낸 뒤 끊김
        for i, c in enumerate(llm.stream(s["messages"])):
            if i == 1:
                raise ConnectionError("끊김")
    return {"messages": [llm.invoke(s["messages"])]}

g = StateGraph(MessagesState)
g.add_node("gen", gen, retry_policy=RetryPolicy(max_attempts=2, initial_interval=0.01))

STEP 3 · 받는 쪽이 재시도를 알아채는 방법 설계

messages 스트림에는 "재시도 시작" 표시가 없습니다. 실제예 ②처럼 노드 첫 줄에서 custom 신호를 보내고, 받는 쪽은 stream_mode=["custom", "messages", "updates"]로 함께 받도록 설계하세요.

힌트 보기

노드 첫 줄: get_stream_writer()({"type": "attempt", "node": "gen"}). 받는 쪽: attempt를 받으면 그 노드의 글자 버퍼를 비움. 노드 이름은 messages 메타데이터의 langgraph_node로 맞춥니다.

예시 답안 보기
def gen(s):
    get_stream_writer()({"type": "attempt", "node": "gen"})
    ...                                              # 나머지 동일

buffers = {}
for mode, data in app.stream(입력, stream_mode=["custom", "messages", "updates"]):
    if mode == "custom" and data.get("type") == "attempt":
        buffers[data["node"]] = ""                   # 새 시도: 그 노드 글자 지우기
    elif mode == "messages":
        c, md = data
        if isinstance(c, AIMessageChunk):
            buffers[md["langgraph_node"]] = buffers.get(md["langgraph_node"], "") + c.content
    elif mode == "updates":
        node = list(data)[0]
        if node == "gen":
            final = data[node]["messages"][-1].content
print(buffers["gen"], "|", final, "|", buffers["gen"] == final)
STEP 4 · 다른 해법들과 비교 (토론)

① 받는 쪽 버퍼 비우기(위) ② 재시도 노드에서는 글자 스트리밍을 끄고 완성본만 보내기 ③ 글자는 보여 주되, 노드가 끝나면 updates의 최종값으로 화면을 덮어쓰기. 사용자 경험과 구현 난이도를 비교하세요.

정리 예

①은 정확하지만 받는 쪽 코드가 복잡합니다. ②는 가장 단순하지만 글자 효과가 사라집니다. ③은 잠깐 겹쳐 보였다가 고쳐지므로 구현이 쉽고 결과는 항상 맞습니다. 실무에선 ③을 기본으로 하고, 자주 끊기는 환경이면 ①을 더합니다.
