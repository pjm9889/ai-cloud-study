0리듀서란

전제 TypedDict로 상태를 정의하고, 노드·엣지로 START → 노드 → END 그래프를 그려 본 상태입니다.

한 문장 정의

노드는 상태 전체가 아니라 바꿀 키만 돌려줍니다. 리듀서는 그 새 값을 기존 값과 어떻게 합칠지 정하는 함수입니다.

기존 값+노드가 돌려준 새 값→리듀서 함수→저장될 값

모양: Annotated[타입, 함수]

from typing import Annotated
from typing_extensions import TypedDict
from operator import add

class RagState(TypedDict):
    question: str                      # 함수 없음 → 새 값으로 덮어쓰기
    docs: Annotated[list[str], add]    # add 함수 → 기존 docs + 새 docs
add는 함수입니다 파이썬 기본 함수로 +와 같습니다. add([1], [2]) → [1, 2]. 직접 만든 함수를 넣어도 똑같이 동작합니다.
def 이어붙이기(old, new):          # 리듀서 = (기존값, 새값)을 받아 합친 값을 돌려주는 함수
    return old + new

docs: Annotated[list[str], 이어붙이기]   # Annotated[list[str], add] 와 같음
이름 주의 add(파이썬 함수) · add_messages(LangGraph의 메시지용 리듀서) · add_node/add_edge(그래프 메서드, 리듀서와 무관)는 서로 다른 것입니다.

더 읽을거리 (위키독스)

  • 1-3-2-3. 리듀서(Reducer) - 상태 업데이트
  • 1-3-2-4. MessagesState - 대화형 앱의 상태 관리

위키독스 1-3-2-4의 operator.add 비교 예시는 role 없는 dict를 쓰는데, 실제 add_messages에서는 ValueError가 납니다. 메시지 객체를 쓰거나 "role"을 넣으세요.

1리듀서 설계 이슈RAGLangGraph 필수

왜 설계가 먼저인가

리듀서를 잘못 고르면 대부분 에러 없이 결과만 틀립니다. 대화가 사라지거나, 횟수를 두 번 세거나, 같은 문서가 두 번 들어갑니다. 그래서 코드를 쓰기 전에 상태의 필드마다 아래 4가지 질문에 답해 두는 것이 리듀서 설계입니다.

필드마다 던질 4가지 질문

Q1. 이 키에 쓰는 노드는 몇 개인가?
하나뿐이면 대개 덮어쓰기로 충분합니다. 여러 노드가 쓰면 Q2, Q3를 꼭 따져 봅니다.
Q2. 같은 단계에서 동시에 쓰는가? (병렬)
그렇다면 리듀서가 반드시 필요합니다. 없으면 InvalidUpdateError로 멈춥니다.
Q3. 새 값이 오면 기존 값은 어떻게 하나?
버린다(최신만 의미) · 쌓는다 · 골라 남긴다(최고값, 중복 제거) · 같은 것만 고친다(id) 중 하나입니다.
Q4. 노드는 무엇을 돌려주나?
"전체 값"인가 "이번에 생긴 몫"인가. 쌓는 리듀서에는 이번 몫만 돌려줘야 합니다. Q3과 한 쌍입니다.

Q3의 답 → 리듀서

새 값이 오면리듀서선언예
버린다 (최신만)없음step: str현재 단계, 재작성한 질문
쌓는다addAnnotated[list, add]검색 문서, 로그, 토큰 수 합계
골라 남긴다직접 만든 함수Annotated[float, keep_max]최고 점수, 중복 없는 문서, 최근 N개
같은 것만 고친다add_messagesMessagesState 상속대화·도구 호출 기록 (id 기준)

설계를 안 하면 생기는 5가지 문제

InvalidUpdateError병렬로 같은 키에 씀 (Q2)add 또는 직접 함수실제예 ①

설계 습관 리듀서는 "상태를 선언할 때" 정해지고, 노드는 그 규칙을 믿고 "자기 몫만" 돌려줍니다. 합치는 책임은 상태 선언에, 계산 책임은 노드에 둡니다.

2실제예 ① 사내 규정 하이브리드 검색RAGLangGraph 필수

STEP 1 · 상황 읽기

사내 규정 챗봇의 검색 품질을 올리려고 벡터 검색과 키워드 검색을 동시에 돌리기로 했습니다. 두 검색기가 찾은 문서를 모아 답변 노드에 넘겨야 합니다.

START→vector_search+keyword_search→answer→END
STEP 2 · 설계표 채우기
필드Q1Q2 동시?Q3Q4리듀서
question입력---없음
docsvector, keyword예쌓음이번 검색 결과add
STEP 3 · 설계를 무시하면? (리듀서 없이 실행)
from typing import Annotated
from typing_extensions import TypedDict
from operator import add
from langgraph.graph import StateGraph, START, END

class SearchState(TypedDict):
    question: str
    docs: list                       # 리듀서 없음

def vector_search(s):  return {"docs": ["v:연차규정", "v:휴가신청"]}
def keyword_search(s): return {"docs": ["k:연차규정"]}
def answer(s):
    print("답변 노드가 받은 문서:", s["docs"])
    return {}

g = StateGraph(SearchState)
g.add_node("vector_search", vector_search)
g.add_node("keyword_search", keyword_search)
g.add_node("answer", answer)
g.add_edge(START, "vector_search")
g.add_edge(START, "keyword_search")                         # 팬아웃: 동시에 실행
g.add_edge(["vector_search", "keyword_search"], "answer")    # 둘 다 끝나면 answer
g.add_edge("answer", END)
g.compile().invoke({"question": "연차 규정"})
InvalidUpdateError: At key 'docs': Can receive only one value per step. Use an Annotated key to handle multiple values.

두 검색 노드는 같은 단계(super-step)에서 실행됩니다. docs에 값이 두 개 들어왔는데 합치는 함수가 없으니 LangGraph가 멈춥니다. Q2에 "예"인데 리듀서를 안 붙인 결과입니다.

STEP 4 · 설계대로 고치기
class SearchState(TypedDict):
    question: str
    docs: Annotated[list, add]       # add 함수를 넣음 → 기존 docs + 새 docs
STEP 5 · 결과 확인
답변 노드가 받은 문서: ['k:연차규정', 'v:연차규정', 'v:휴가신청']
  1. 병렬이면 리듀서. Send API, 멀티에이전트도 똑같습니다.
  2. 노드 코드는 그대로. 검색 노드는 "내가 찾은 것"만 돌려주고, 합치기는 상태 선언이 맡습니다.
  3. 순서는 보장되지 않는다. 정렬이 필요하면 리듀서에서 합니다.
설계 다시 보기 '연차규정'이 두 번 들어갔습니다. Q3의 답이 사실은 "쌓음"이 아니라 "골라 남김(중복 제거)"이었던 것입니다. 이것을 고치는 것이 미션 M4입니다.

3실제예 ② 쇼핑몰 챗봇 · 상담원 답변 검토LangGraph 필수MCP·에이전트

STEP 1 · 상황 읽기

쇼핑몰 챗봇이 "환불은 7일"이라고 잘못 답했습니다. 상담원이 검토 단계에서 "14일"로 고쳐 같은 메시지를 다시 넣습니다(Human-in-the-Loop). 대화 기록에는 고친 답만 남아야 합니다.

STEP 2 · 설계표 채우기
필드Q1Q2Q3 새 값이 오면Q4리듀서
messages사용자, LLM, 상담원아니오새 메시지는 쌓고, 같은 메시지는 고침새 메시지 또는 같은 id의 수정본add_messages

"쌓기"와 "고치기"가 섞여 있습니다. add는 쌓기만 할 줄 알기 때문에 맞지 않습니다.

STEP 3 · add와 add_messages 비교
from operator import add
from langgraph.graph.message import add_messages
from langchain_core.messages import HumanMessage, AIMessage, RemoveMessage

q      = HumanMessage(content="환불 기간이 어떻게 되나요?", id="h-1")
draft  = AIMessage(content="환불은 7일 이내 가능합니다.", id="ai-1")
edited = AIMessage(content="환불은 구매 후 14일 이내 가능합니다. (검토 완료)", id="ai-1")   # 같은 id

r1 = add([q, draft], [edited])
r2 = add_messages([q, draft], [edited])
print("add          :", len(r1), [m.content for m in r1])
print("add_messages :", len(r2), [m.content for m in r2])

add로 쌓으면 다음 LLM 호출 때 모델이 "7일"과 "14일"을 둘 다 봅니다. add_messages는 id가 같으면 그 자리에서 교체합니다.

STEP 5 · 그래프에 넣기 (MessagesState)
from langgraph.graph import MessagesState

class ShopState(MessagesState):      # messages: Annotated[list, add_messages] 내장
    order_id: str

def review(state: ShopState):        # 상담원 검토 노드
    last = state["messages"][-1]
    fixed = last.content.replace("7일", "구매 후 14일") + " (검토 완료)"
    return {"messages": [AIMessage(content=fixed, id=last.id)]}   # id 유지 = 교체
  1. 대화는 add가 아니라 add_messages. 수정·삭제가 되어야 HITL과 메모리 정리를 할 수 있습니다.
  2. 수정의 열쇠는 id. id를 유지하면 교체, 새 id면 추가입니다.
  3. dict로 보내려면 role 필수. {"role": "assistant", "id": "ai-1", "content": "..."}

class ChatState(TypedDict):

    chat_history: list

def counsel(state: ChatState):

g.add_edge(START, "counsel"); g.add_edge("counsel", END)

M2. 재검색 RAG의 최종 상태 예측

STEP 1 · 상황 읽기

검색 → 질문 재작성 → 재검색 순서로 도는 RAG입니다. 네 필드에 서로 다른 리듀서가 붙어 있습니다.

def keep_max(old: float, new: float) -> float:     # 직접 만든 리듀서: 더 큰 값만 남김
    return max(old, new)

class RagState(TypedDict):
    step: str
    logs: Annotated[list[str], add]
    best_score: Annotated[float, keep_max]
    retry: int

def retrieve(s):  return {"step": "retrieve",  "logs": ["검색 5건"],   "best_score": 0.62, "retry": 1}
def rewrite(s):   return {"step": "rewrite",   "logs": ["질문 재작성"], "best_score": 0.48}
def retrieve2(s): return {"step": "retrieve2", "logs": ["재검색 5건"], "best_score": 0.81, "retry": s["retry"] + 1}

# START → retrieve → rewrite → retrieve2 → END
# invoke({"step": "start", "logs": ["시작"], "best_score": 0.0, "retry": 0})
STEP 2 · 설계 거꾸로 읽기

코드에서 각 필드의 Q3 답(버림 / 쌓음 / 골라 남김)을 읽어 내세요.

확인

step = 버림 · logs = 쌓음 · best_score = 골라 남김(최고) · retry = 버림(노드가 직접 계산한 값으로 덮어씀)

M3. 재시도 3번인데 횟수가 7?

STEP 1 · 상황 읽기

"재시도 3번 넘으면 중단" 규칙을 넣었는데, 질문 재작성을 3번 했을 뿐인데 retry가 7로 찍혀 너무 일찍 중단됩니다.

class S(TypedDict):
    question: str
    retry: Annotated[int, add]

def rewrite(s):
    return {"retry": s["retry"] + 1}

# START → rewrite1 → rewrite2 → rewrite3 → END  (세 노드 모두 rewrite 함수)
# invoke({"question": "연차", "retry": 0})
STEP 2 · 설계표의 Q3과 Q4 비교

retry에 대해 "리듀서가 기대하는 것(Q3)"과 "노드가 실제로 돌려주는 것(Q4)"을 각각 적으세요.

확인

Q3: add = 쌓음 → 노드는 이번 몫(1)을 돌려줘야 함. Q4: 노드는 누적값(기존+1)을 돌려줌. 짝이 안 맞습니다.

STEP 3 · 한 단계씩 계산

저장값 = add(기존값, 노드 반환값)을 세 번 계산해 보세요.

계산 확인
# rewrite1: 반환 0+1=1 → add(0, 1) = 1
# rewrite2: 반환 1+1=2 → add(1, 2) = 3
# rewrite3: 반환 3+1=4 → add(3, 4) = 7
{'question': '연차', 'retry': 7}
STEP 4 · 두 가지 방법으로 고치기

방법 ① 리듀서는 그대로 두고 노드를 고친다. 방법 ② 노드는 그대로 두고 리듀서를 고친다.

예시 답안 보기
# 방법 ① 리듀서 유지, 노드는 '이번 몫'만
def rewrite(s): return {"retry": 1}

# 방법 ② 노드 유지, 리듀서 제거(덮어쓰기)
class S(TypedDict):
    question: str
    retry: int
{'question': '연차', 'retry': 3}
STEP 5 · 설계 판단

나중에 재작성 노드 두 개가 동시에 retry를 올리게 바뀐다면, 어느 방법만 쓸 수 있을까요?

확인

방법 ①만 됩니다. 방법 ②는 리듀서가 없어 같은 단계에 두 값이 들어오면 InvalidUpdateError(실제예 ①)입니다. 리듀서와 노드 반환값은 한 쌍으로 설계해야 합니다.

M4. 중복 문서를 합치는 리듀서 만들기

STEP 1 · 상황 읽기

실제예 ①에서 남은 문제입니다. 벡터 검색과 BM25 검색이 같은 문서(HR-01)를 서로 다른 점수로 가져옵니다. add로 쌓으면 같은 문서가 두 번 LLM에 들어갑니다.

def vec(s):  return {"docs": [{"doc_id": "HR-01", "score": 0.82, "by": "vector"},

def bm25(s): return {"docs": [{"doc_id": "HR-01", "score": 0.91, "by": "bm25"},

STEP 2 · 설계: 합치는 규칙을 말로 적기

코드 전에 "새 문서가 오면 기존 문서와 어떻게 합칠지"를 규칙 3줄로 적으세요. (중복일 때 · 순서 · 개수)

규칙 확인

① doc_id가 같으면 score가 높은 쪽만 남김 ② score 내림차순 ③ 상위 5개만 (LLM 컨텍스트 제한)

STEP 3 · 리듀서 함수만 먼저 만들고 단독 테스트
def merge_docs(old: list[dict], new: list[dict]) -> list[dict]:
    ...   # 여기를 채우기

print(merge_docs([], vec(None)["docs"]))                        # 첫 호출: old가 비어 있음
print(merge_docs(vec(None)["docs"], bm25(None)["docs"]))        # 두 번째 호출
힌트 보기

doc_id를 키로 하는 dict에 담으면 중복이 저절로 정리됩니다. 마지막에 sorted(..., key=lambda d: d["score"], reverse=True)[:5].

예시 답안 보기
def merge_docs(old: list[dict], new: list[dict]) -> list[dict]:
    best = {d["doc_id"]: d for d in (old or [])}
    for d in (new or []):
        cur = best.get(d["doc_id"])
        if cur is None or d["score"] > cur["score"]:
            best[d["doc_id"]] = d
    return sorted(best.values(), key=lambda d: d["score"], reverse=True)[:5]
STEP 4 · 상태에 연결하고 그래프 실행
class DocState(TypedDict):
    question: str
    docs: Annotated[list[dict], merge_docs]     # 직접 만든 함수를 넣음

g = StateGraph(DocState)
g.add_node("vec", vec); g.add_node("bm25", bm25)
g.add_edge(START, "vec"); g.add_edge(START, "bm25")
g.add_edge("vec", END);   g.add_edge("bm25", END)
for d in g.compile().invoke({"question": "연차"})["docs"]:
    print(d)

M5. 길어진 IT 상담 대화 정리하기

STEP 1 · 상황 읽기

IT 헬프데스크 에이전트의 대화가 길어져 토큰 비용이 커졌습니다. 오래된 메시지는 요약해 두고 지워야 합니다. 대화에는 도구 호출도 섞여 있습니다.

from langchain_core.messages import (HumanMessage, AIMessage, SystemMessage,
                                     ToolMessage, RemoveMessage)
class SupportState(MessagesState):
    summary: NotRequired[str]

seed = [SystemMessage(content="너는 사내 IT 상담원이다", id="sys")]
for i in range(4):
    seed += [HumanMessage(content=f"질문{i}", id=f"h{i}"), AIMessage(content=f"답변{i}", id=f"a{i}")]
seed += [HumanMessage(content="VPN 안돼요", id="h9"),
         AIMessage(content="", id="a9", tool_calls=[{"name": "check_vpn", "args": {}, "id": "call1"}]),
         ToolMessage(content="VPN 서버 정상", tool_call_id="call1", id="t9"),
         AIMessage(content="서버는 정상입니다. 재접속해 보세요.", id="a10")]
STEP 2 · 설계: 누가 무엇을 책임지나

messages(add_messages)와 summary 각각에 대해 Q3을 답하고, "무엇을 지울지"는 리듀서와 노드 중 누가 정해야 하는지 적으세요.

확인

messages: 같은 id 고침 + RemoveMessage면 삭제 → add_messages. summary: 노드가 기존 요약에 이어 붙여 돌려줌 → 덮어쓰기. 리듀서는 시키는 대로 지울 뿐이므로 무엇을 지울지는 노드가 책임집니다.

STEP 3 · 단순 버전 만들기

규칙: ① SystemMessage는 지우지 않는다 ② 시스템 메시지를 뺀 대화가 10개 이하면 아무것도 안 한다 ③ 넘으면 최근 KEEP_LAST = 2개만 남기고 나머지는 summary에 붙인 뒤 RemoveMessage로 삭제 (요약은 LLM 대신 각 메시지 앞 15글자를 " / "로 이어 붙여도 됨)

힌트 보기

convo = [m for m in msgs if not isinstance(m, SystemMessage)], cut = len(convo) - KEEP_LAST, 지울 것은 convo[:cut].

단순 버전 결과
남은 메시지: [('SystemMessage', 'sys'), ('ToolMessage', 't9'), ('AIMessage', 'a10')]

도구를 부른 AIMessage(a9)는 지워지고 결과(t9)만 남았습니다.

STEP 4 · 문제 찾고 규칙 추가하기

OpenAI·Anthropic API는 ToolMessage 앞에 그 tool_call_id를 가진 AIMessage가 있어야 합니다. 짝이 깨지면 다음 LLM 호출이 400 에러로 실패합니다. 규칙 ④를 추가하세요: 남길 구간이 ToolMessage로 시작하면, 그 도구를 부른 AIMessage도 함께 남긴다.

힌트 보기

convo[cut]이 ToolMessage인 동안 cut을 한 칸씩 앞으로 옮깁니다.

예시 답안 보기
KEEP_LAST = 2

def summarize_old(state: SupportState):
    convo = [m for m in state["messages"] if not isinstance(m, SystemMessage)]   # ①
    if len(convo) <= 10:                                                        # ②
        return {}
    cut = len(convo) - KEEP_LAST
    while cut > 0 and isinstance(convo[cut], ToolMessage):                     # ④
        cut -= 1
    old = convo[:cut]
    text = " / ".join(str(m.content)[:15] for m in old)        # 실제로는 LLM 요약
    prev = state.get("summary", "")
    return {"summary": (prev + " | " if prev else "") + text,  # ③
            "messages": [RemoveMessage(id=m.id) for m in old]}

g = StateGraph(SupportState)
g.add_node("summarize", summarize_old)
g.add_edge(START, "summarize"); g.add_edge("summarize", END)
out = g.compile().invoke({"messages": seed})
print("남은 메시지:", [(type(m).__name__, m.id) for m in out["messages"]])
남은 메시지: [('SystemMessage', 'sys'), ('AIMessage', 'a9'), ('ToolMessage', 't9'), ('AIMessage', 'a10')]
