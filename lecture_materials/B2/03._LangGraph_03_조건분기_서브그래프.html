학습 목표
  • 조건부 엣지로 여러 갈래 흐름을 만들고, 기본 경로와 루프 종료 조건을 빠뜨리지 않는다.
  • 그래프를 서브그래프로 나눌지 판단하고, 두 가지 연결 방법(노드로 추가 / 래퍼 노드에서 호출) 중 하나를 이유를 들어 고른다.
  • 공유 키 · 리듀서 · 체크포인터 때문에 생기는 서브그래프 버그를 진단한다.
  • 분기 + 서브그래프를 조합해 "질문 유형별 전문 모듈"과 "재사용 결재 모듈"을 만든다.
전제 01 리듀서, 02 노드·엣지(조건부 엣지 · Command · 루프)를 마쳤습니다.

1조건분기 다시 보기LangGraph 필수

서브그래프와 함께 쓸 때 가장 많이 쓰는 것이 조건분기입니다. 02에서 배운 것 중 꼭 필요한 것만 다시 정리합니다.

모양: 라우터 함수 + 후보

from typing import Literal

def route(state) -> Literal["faq", "calc", "fallback"]:     # ① 후보 전부를 타입힌트로
    if "계산" in state["question"]:
        return "calc"
    if "연차" in state["question"]:
        return "faq"
    return "fallback"                                       # ② 기본 경로

g.add_conditional_edges("classify", route)                 # 출발 노드, 라우터
classify→route(state)→faq/calc/fallback

체크리스트 4가지

  1. 후보를 전부 적었나? 라우터가 돌려줄 수 있는 값이 경로 맵(또는 Literal)에 다 있어야 합니다. 없으면 KeyError.
  2. 기본 경로가 있나? 마지막 return이 "모르는 경우"를 받아야 합니다. LLM이 분류할 때는 특히 중요합니다.
  3. 라우터는 읽기만 하나? 라우터 안에서 상태를 바꿔도 저장되지 않습니다. 횟수 증가 같은 일은 노드가 합니다.
  4. 되돌아가는 길에 탈출구가 있나? 성공 조건과 포기 조건(횟수) 두 개, 그리고 recursion_limit.

조건부 엣지 vs Command (02 복습)

조건부 엣지Command
어디에 쓰나노드 밖, 라우터 함수노드 안, 반환값
상태 변경불가 (고르기만)가능 (update=)
서브그래프와부모에서 "어느 서브그래프로" 고를 때서브그래프 안에서 부모 노드로 넘길 때 graph=Command.PARENT
이번 단원에서의 분기 위치 "어느 모듈로 갈지"는 부모 그래프에서, "모듈 안에서 어떻게 처리할지"는 서브그래프 안에서 분기합니다. 분기를 어디에 둘지가 서브그래프 설계의 일부입니다.

2서브그래프 설계 이슈RAGMCP·에이전트

서브그래프란

컴파일된 그래프를 다른 그래프의 노드 하나처럼 쓰는 것입니다. 함수를 나눠 모듈로 만드는 것과 같습니다. 문제는 부모와 서브그래프가 상태를 어떻게 주고받느냐에서 생깁니다.

서브그래프를 만들 때 던질 5가지 질문

Q1. 정말 묶을 가치가 있나?
여러 그래프에서 재사용하거나, 따로 개발·테스트하거나, 에이전트마다 독립 상태가 필요할 때 묶습니다. 아니면 노드 몇 개로 충분합니다.
Q2. 부모와 상태 키를 공유하나?
공유하면 방법 1: add_node("이름", 컴파일된_서브그래프). 키 이름이 다르면 방법 2: 래퍼 노드 안에서 subgraph.invoke()로 부모 → 서브 → 부모 변환.
Q3. 공유 키에 리듀서가 있나?
방법 1에서 서브그래프는 끝날 때 공유 키의 전체 값을 부모에 돌려줍니다. 덮어쓰기 키는 괜찮지만, add 키는 부모가 이미 가진 값이 한 번 더 더해집니다. (add_messages는 id로 합쳐서 괜찮습니다.)
Q4. 분기는 어디에 두나?
"어느 서브그래프로"는 부모에서, "서브그래프 안의 세부 흐름"은 서브그래프 안에서 분기합니다. 서브그래프 결과로 부모가 되돌아가는 루프라면 탈출 조건(횟수)은 부모 상태에 둡니다.
Q5. 멈추고 기다리거나(interrupt) 기억해야 하나?
체크포인터는 부모에만 넣으면 서브그래프로 전파됩니다. 서브그래프가 따로 기억해야 할 때만 서브그래프를 compile(checkpointer=True)로 컴파일합니다.

Q2의 답 → 연결 방법

방법 1: 노드로 추가방법 2: 래퍼 노드에서 호출
코드g.add_node("search", search_graph)def call(s): r = sub.invoke({...}); return {...}
상태같은 이름의 키가 자동으로 오감직접 변환 (이름이 달라도 됨)
서브 전용 키부모에 안 보임부모에 안 보임
좋은 때question · context처럼 키가 같을 때스키마가 다를 때, 공유 키 리듀서 문제를 피할 때, 에이전트별 독립 메시지
상태 조회·interrupt둘 다 됩니다 (단, 도구 함수 안에서 호출하면 안 됨)

설계를 안 하면 생기는 5가지 문제

증상원인 (놓친 질문)해결어디서
서브 전용 키가 결과에 없음정상 동작 (캡슐화) — 몰랐을 뿐 (Q2)subgraphs=True 스트림으로 확인M2
KeyError: 'text'공유 키가 없는데 방법 1로 붙임 (Q2)방법 2 래퍼M3
로그·문서가 두 번 들어감add 리듀서 공유 키 (Q3)래퍼에서 새 몫만, 또는 공유 안 함M4

RuntimeError (checkpointer=True)부모에 True를 씀 (Q5)부모엔 InMemorySaver()M7

3서브그래프 문법 한 장LangGraph 필수

방법 1: 컴파일한 서브그래프를 노드로 추가 (키 공유)

sub = sub_builder.compile()               # 서브그래프는 따로 만들고 컴파일
parent.add_node("search", sub)            # 노드처럼 추가 (함수 자리에 그래프)
parent.add_edge("receive", "search")

방법 2: 래퍼 노드에서 호출 (키가 다름)

def call_translator(s: ParentState):
    r = translate_graph.invoke({"src": s["answer_ko"], "lang": "en"})   # 부모 → 서브
    return {"answer_en": r["out"]}                                       # 서브 → 부모
parent.add_node("translate", call_translator)

서브그래프 안까지 보기

for ns, upd in app.stream(입력, stream_mode="updates", subgraphs=True):
    print(ns, upd)        # ns == () 이면 부모, ('search:…',) 이면 search 서브그래프 안
app.get_graph(xray=True).draw_mermaid()   # 그림에 서브그래프 내부까지 표시

체크포인터 · interrupt · 상태 조회

from langgraph.checkpoint.memory import InMemorySaver

app = parent.compile(checkpointer=InMemorySaver())     # 부모에만. 서브그래프로 전파됨
# parent.compile(checkpointer=True)  ← 부모에는 불가 (RuntimeError)
# sub_builder.compile(checkpointer=True)  ← 서브그래프가 따로 기억해야 할 때만

cfg = {"configurable": {"thread_id": "t-1"}}
app.invoke(입력, cfg)                                 # 서브그래프 안 interrupt 에서 멈춤
st = app.get_state(cfg, subgraphs=True)
st.tasks[0].state.values                               # 멈춘 서브그래프의 상태
app.invoke(Command(resume="승인"), cfg)               # 재개

return Command(goto="human_agent", graph=Command.PARENT, update={"messages": [...]})

4실제예 ① 사내 규정 검색 서브그래프 재사용RAGLangGraph 필수

STEP 1 · 상황 읽기

사내 규정 검색(키워드 추출 → 문서 조회)을 HR 챗봇, IT 챗봇, 신입 온보딩 봇에서 모두 쓰려 합니다. 검색 부분을 서브그래프로 만들어 붙입니다.

STEP 2 · 설계 (Q1~Q3)
질문답
Q1 묶을 가치세 챗봇에서 재사용 → 예
Q2 공유 키question(입력), context(출력)를 부모와 같은 이름으로 → 방법 1
Q3 리듀서공유 키 둘 다 덮어쓰기 → 문제 없음. keywords는 서브 전용
STEP 3 · 서브그래프 만들고 단독 테스트
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

DOCS = {"연차": "연차는 입사 1년 후 15일", "출장": "출장 일비는 5만원", "보안": "비밀번호는 90일마다 변경"}

class SearchState(TypedDict):
    question: str          # 공유 (입력)
    context: str           # 공유 (출력)
    keywords: list[str]    # 서브그래프 전용

def extract(s): return {"keywords": [k for k in DOCS if k in s["question"]]}
def lookup(s):  return {"context": " / ".join(DOCS[k] for k in s["keywords"]) or "관련 문서 없음"}

sb = StateGraph(SearchState)
sb.add_node("extract", extract); sb.add_node("lookup", lookup)
sb.add_edge(START, "extract"); sb.add_edge("extract", "lookup"); sb.add_edge("lookup", END)
search_graph = sb.compile()

print(search_graph.invoke({"question": "연차랑 출장 규정 알려줘"}))
{'question': '연차랑 출장 규정 알려줘', 'context': '연차는 입사 1년 후 15일 / 출장 일비는 5만원', 'keywords': ['연차', '출장']}
STEP 4 · 부모 그래프에 노드로 붙이기
class QaState(TypedDict):          # 부모: keywords 없음
    question: str
    context: str
    answer: str

def generate(s): return {"answer": f"답변: {s['context']}"}

pb = StateGraph(QaState)
pb.add_node("search", search_graph)            # 방법 1
pb.add_node("generate", generate)
pb.add_edge(START, "search"); pb.add_edge("search", "generate"); pb.add_edge("generate", END)
qa = pb.compile()

for ns, upd in qa.stream({"question": "연차 며칠이야?"}, stream_mode="updates", subgraphs=True):
    print(ns[0].split(":")[0] if ns else "(부모)", upd)
STEP 5 · 결과 확인
search {'extract': {'keywords': ['연차']}}
search {'lookup': {'context': '연차는 입사 1년 후 15일'}}
(부모) {'search': {'question': '연차 며칠이야?', 'context': '연차는 입사 1년 후 15일'}}
(부모) {'generate': {'answer': '답변: 연차는 입사 1년 후 15일'}}
  1. 서브 전용 키는 부모에 안 간다. 부모가 받은 업데이트에는 question, context만 있고 keywords는 없습니다.
  2. 단독 테스트가 된다. 서브그래프는 그 자체로 그래프라서 따로 invoke해 검증할 수 있습니다. 팀 단위 개발의 장점입니다.
  3. 재사용은 붙이기만. IT 챗봇에도 add_node("search", search_graph) 한 줄이면 됩니다(키 이름만 맞으면).

5실제예 ② 스키마가 다른 번역 모듈LangGraph 필수MCP·에이전트

STEP 1 · 상황 읽기

다른 팀이 만든 번역 서브그래프(src, lang → out)를 글로벌 사내 챗봇에 붙이려 합니다. 부모는 answer_ko, answer_en이라는 키를 씁니다. 번역 팀 코드는 바꿀 수 없습니다.

STEP 2 · 설계 (Q2)

공유하는 키 이름이 하나도 없습니다 → 방법 2. 래퍼 노드가 "부모 → 서브 입력"과 "서브 출력 → 부모"를 변환하는 어댑터 역할을 합니다.

answer_ko→래퍼: src=answer_ko→번역 서브그래프→래퍼: answer_en=out
STEP 3 · 번역 서브그래프 (다른 팀 코드)
class TranslateState(TypedDict):
    src: str
    lang: str
    out: str

def translate(s):
    table = {"연차는 입사 1년 후 15일": "15 days of annual leave after 1 year"}
    return {"out": table.get(s["src"], f"[{s['lang']}] {s['src']}")}

tb = StateGraph(TranslateState)
tb.add_node("translate", translate); tb.add_edge(START, "translate")
translate_graph = tb.compile()
STEP 4 · 부모 그래프와 래퍼 노드
class GlobalQa(TypedDict):
    question: str
    answer_ko: str
    answer_en: str

def answer_ko(s): return {"answer_ko": "연차는 입사 1년 후 15일"}

def call_translator(s: GlobalQa):
    r = translate_graph.invoke({"src": s["answer_ko"], "lang": "en"})   # 부모 → 서브
    return {"answer_en": r["out"]}                                       # 서브 → 부모

gb = StateGraph(GlobalQa)
gb.add_node("answer_ko", answer_ko); gb.add_node("translate", call_translator)
gb.add_edge(START, "answer_ko"); gb.add_edge("answer_ko", "translate"); gb.add_edge("translate", END)
print(gb.compile().invoke({"question": "연차 며칠?"}))
STEP 5 · 결과 확인
{'question': '연차 며칠?', 'answer_ko': '연차는 입사 1년 후 15일', 'answer_en': '15 days of annual leave after 1 year'}
  1. 래퍼 = 어댑터. 남의 모듈을 고치지 않고 이름만 맞춰 끼웁니다.
  2. 무엇이 오가는지 눈에 보인다. 방법 1과 달리 넘기는 값과 받는 값이 코드에 드러나 실수가 적습니다.

M5. 끝나지 않는 재처리 (위키독스 1-5-2 패턴)

STEP 1 · 상황 읽기

로그 검증 서브그래프가 error를 돌려주면 부모가 전처리부터 다시 합니다. 위키독스 1-5-2와 같은 구조입니다. 입력에 "ERR"가 들어 있으면 멈추지 않습니다.

class CheckSub(TypedDict):
    text: str
    status: str
def check(s): return {"status": "error" if "ERR" in s["text"] else "ok"}
csb = StateGraph(CheckSub); csb.add_node("check", check); csb.add_edge(START, "check")
check_graph = csb.compile()

class Pipeline(TypedDict):
    text: str
    status: str
    result: str
def prepare(s): return {"text": s["text"].strip()}
def finish(s):  return {"result": f"완료: {s['text']}"}
def route(s) -> Literal["finish", "prepare"]:
    return "prepare" if s["status"] == "error" else "finish"

b = StateGraph(Pipeline)
b.add_node("prepare", prepare); b.add_node("check", check_graph); b.add_node("finish", finish)
b.add_edge(START, "prepare"); b.add_edge("prepare", "check")
b.add_conditional_edges("check", route); b.add_edge("finish", END)
b.compile().invoke({"text": " ERR 로그 "}, {"recursion_limit": 25})
STEP 2 · 설계 점검 (Q4)

재처리해도 결과가 바뀔 수 있나요? 탈출 조건은 부모와 서브그래프 중 어디에 둬야 하나요?

확인

prepare는 공백만 지우므로 몇 번을 돌아도 ERR는 그대로입니다. 루프는 부모 그래프에 있으므로 횟수와 포기 경로도 부모 상태에 둡니다. 서브그래프는 매번 새로 실행되어 이전 횟수를 기억하지 못합니다.

힌트 보기

    status: str
    retry: Annotated[int, add]

def prepare(s): return {"text": s["text"].strip(), "retry": 1}

def route(s) -> Literal["finish", "prepare", "give_up"]:
    if s["status"] == "ok":
        return "finish"
    return "prepare" if s["retry"] < 3 else "give_up"

b.add_node("give_up", give_up); b.add_edge("give_up", END)

import re
FAQ = {"연차": "연차는 15일", "주차": "주차는 B2 층"}

class FaqSub(TypedDict):
    question: str; answer: str; hits: list[str]
# find: hits 채우기 → compose: answer 만들기 (없으면 "FAQ에 없음")

class CalcSub(TypedDict):
    question: str; answer: str; expr: str
# parse: 질문에서 숫자·연산자만 뽑아 expr → calc: answer = "식 = 결과"
예시 답안 보기
fb = StateGraph(FaqSub)
fb.add_node("find", lambda s: {"hits": [v for k, v in FAQ.items() if k in s["question"]]})
fb.add_node("compose", lambda s: {"answer": s["hits"][0] if s["hits"] else "FAQ에 없음"})
fb.add_edge(START, "find"); fb.add_edge("find", "compose")
faq_graph = fb.compile()

cb = StateGraph(CalcSub)
cb.add_node("parse", lambda s: {"expr": "".join(re.findall(r"[\d+\-*/(). ]", s["question"])).strip()})
cb.add_node("calc", lambda s: {"answer": f"{s['expr']} = {eval(s['expr'])}"})   # 교육용. 실무에선 eval 금지
cb.add_edge(START, "parse"); cb.add_edge("parse", "calc")
calc_graph = cb.compile()
STEP 4 · 부모 그래프: 분기 + 서브그래프
예시 답안 보기
class Ask(TypedDict):
    question: str
    answer: str

def route_ask(s) -> Literal["calc", "faq", "fallback"]:
    if re.search(r"\d+\s*[+\-*/]\s*\d+", s["question"]): return "calc"
    if any(k in s["question"] for k in FAQ): return "faq"
    return "fallback"

ab = StateGraph(Ask)
ab.add_node("calc", calc_graph); ab.add_node("faq", faq_graph)
ab.add_node("fallback", lambda s: {"answer": "담당자에게 연결합니다"})
ab.add_conditional_edges(START, route_ask)
for n in ["calc", "faq", "fallback"]:
    ab.add_edge(n, END)
ask = ab.compile()

for q in ["출장비 3 * 50000 + 20000 계산해줘", "연차 며칠이야?", "회식 언제야?"]:
    print(q, "→", ask.invoke({"question": q})["answer"])
출장비 3 * 50000 + 20000 계산해줘 → 3 * 50000 + 20000 = 170000
연차 며칠이야? → 연차는 15일
회식 언제야? → 담당자에게 연결합니다
STEP 5 · 확인과 확장
연결 route_ask 자리에 LLM 분류기를, 각 서브그래프 자리에 RAG·도구 에이전트를 넣으면 "라우터 + 전문 에이전트" 구조의 멀티 에이전트가 됩니다.

M7. 결재 서브그래프를 휴가·구매 두 곳에서 재사용 (HITL)

STEP 1 · 상황 읽기

팀장 결재(사람이 승인/반려를 입력)를 서브그래프 하나로 만들어 휴가 신청과 구매 요청 두 워크플로우에서 씁니다. 구매는 10만원 미만이면 결재 없이 자동 승인합니다.

STEP 2 · 설계 (Q1, Q2, Q5)

결재 서브그래프의 상태 키, 각 부모와의 공유 키, 체크포인터를 어디에 넣을지 정하세요.

확인
  • 결재 서브그래프: request(입력), approved(출력) — 두 부모 모두 같은 이름을 쓰게 해 방법 1로 붙임
  • 휴가: 결재 → 상태 기록 / 구매: 금액으로 분기 → 결재 또는 자동 승인 → 상태 기록
  • interrupt로 멈추고 재개해야 하므로 체크포인터 필요 → 부모에만 InMemorySaver(). 서브그래프는 그냥 compile()
STEP 3 · 결재 서브그래프
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

class Approval(TypedDict):
    request: str
    approved: bool

def ask_manager(s):
    decision = interrupt({"승인 요청": s["request"]})     # 여기서 멈춤
    return {"approved": decision == "승인"}

apb = StateGraph(Approval)
apb.add_node("ask_manager", ask_manager); apb.add_edge(START, "ask_manager")
approval_graph = apb.compile()                           # 체크포인터 없이
STEP 4 · 부모 두 개 만들기

① Leave: approval → status("휴가 등록"/"휴가 반려") ② Purchase: START에서 금액 분기(≥ 100000이면 approval, 아니면 auto) → status. 둘 다 compile(checkpointer=InMemorySaver()).

힌트 보기

먼저 부모에 compile(checkpointer=True)를 넣어 실행해 보고 에러 메시지를 확인하세요. 위키독스 설명과 무엇이 다른가요?

예시 답안 보기
class Leave(TypedDict):
    request: str; approved: bool; status: str
class Purchase(TypedDict):
    request: str; amount: int; approved: bool; status: str

def leave_status(s):    return {"status": "휴가 등록" if s["approved"] else "휴가 반려"}
def purchase_route(s) -> Literal["approval", "auto"]:
    return "approval" if s["amount"] >= 100000 else "auto"
def purchase_auto(s):   return {"approved": True, "status": "자동 승인(10만원 미만)"}
def purchase_status(s): return {"status": "구매 진행" if s["approved"] else "구매 반려"}

lb = StateGraph(Leave)
lb.add_node("approval", approval_graph); lb.add_node("status", leave_status)
lb.add_edge(START, "approval"); lb.add_edge("approval", "status"); lb.add_edge("status", END)
leave_app = lb.compile(checkpointer=InMemorySaver())

pub = StateGraph(Purchase)
pub.add_node("approval", approval_graph); pub.add_node("auto", purchase_auto)
pub.add_node("status", purchase_status)
pub.add_conditional_edges(START, purchase_route)
pub.add_edge("approval", "status"); pub.add_edge("auto", END); pub.add_edge("status", END)
purchase_app = pub.compile(checkpointer=InMemorySaver())
RuntimeError: checkpointer=True cannot be used for root graphs.   ← 부모에 True 를 넣었을 때
STEP 5 · 멈추고, 들여다보고, 재개하기
cfg = {"configurable": {"thread_id": "leave-1"}}
r = leave_app.invoke({"request": "11/20 연차 1일", "approved": False, "status": ""}, cfg)
print("멈춤:", r["__interrupt__"][0].value)
st = leave_app.get_state(cfg, subgraphs=True)
print("다음 노드:", st.next, "| 서브그래프 상태:", st.tasks[0].state.values)
print("재개:", leave_app.invoke(Command(resume="승인"), cfg)["status"])
# 구매: 350000원 → 반려 / 30000원 → 자동 승인
