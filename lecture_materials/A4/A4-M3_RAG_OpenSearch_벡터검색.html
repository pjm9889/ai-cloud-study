00. 한 문단 요약 — 우리가 풀려는 문제

기계적인 단계로 들어가기 전에, 이 기술이 “무엇을 위해” 존재하는지부터 이야기합니다. 모듈을 마치면 아래 문단을 스스로 설명할 수 있어야 합니다.

이 탭의 흐름

  1. 모듈 전체를 한 문단으로
  2. LLM의 세 가지 한계
  3. 공통 원인과 RAG의 출발점
이 모듈의 한 문단

“긴 문서를 작은 조각(Chunk)으로 나누고, 각 조각의 의미를 숫자(벡터)로 바꿔 OpenSearch에 저장해 둔다. 사용자가 질문하면 질문도 같은 방식으로 숫자로 바꿔, 저장된 조각 중 의미가 가까운 것 몇 개(k-NN)를 찾아, 그 근거를 LLM에게 넘겨 답을 만들게 한다. 이 전체 구조가 RAG다.”

지금 이 문장이 낯설어도 괜찮습니다. 아래에서 하나씩, 왜 그렇게 하는지를 순서대로 풀어 갑니다.

LLM을 실무에 그대로 쓰기 어려운 세 가지 이유

① 내 자료를 모른다
회사 내부 규정, 팀 매뉴얼, 개인이 가진 PDF는 모델이 학습한 적이 없습니다. 물어봐도 알 수 없습니다.
② 최신 정보를 모른다
모델은 특정 시점까지의 데이터로 학습됩니다. 그 이후에 바뀐 규정·수치·사건은 반영되어 있지 않습니다.
③ 근거 없이 답할 수 있다
모르는 것도 그럴듯하게 지어내는 경향(환각)이 있습니다. 출처가 없으면 신뢰하기 어렵습니다.
이렇게 풀어서 설명합니다

세 문제의 공통 원인은 하나입니다. 모델의 머릿속(학습된 지식)에만 의존하기 때문입니다. 그렇다면 답을 만들기 직전에, 필요한 자료를 찾아서 같이 건네주면 어떨까요? 이것이 RAG의 출발점입니다.

벡터좌표, 임베딩, 차원

실습 환경 전제

A4-M1(Dashboard·Python 연결)과 A4-M2(쿼리 문법)를 마친 상태를 기준으로 합니다. 이 모듈의 bool, filter, match는 A4-M2에서 배운 그대로이고, 새로 더해지는 것은 벡터 검색 knn입니다. 환경은 A4-M1과 같습니다. Docker의 opensearch(9200)와 opensearch-dashboards(5601)가 실행 중이어야 합니다. 서버는 로그인 방식(https, admin 계정)입니다. Python 실습(14~18탭)에는 opensearch-py, sentence-transformers, python-dotenv가 필요하고, OpenSearch 비밀번호는 .env 파일에서 읽습니다. 마지막 답변 생성 단계에서만 LLM API 키를 씁니다(없어도 검색까지는 모두 됩니다).

01. 오픈북 시험과 의미 검색 — 왜 “숫자”가 필요한가

RAG는 오픈북 시험입니다. 그런데 “관련 페이지를 펼친다”를 기계에게 시키려면, 단어가 달라도 뜻이 같으면 찾아 주는 검색이 필요합니다. 그 검색을 위해 의미를 숫자로 바꿉니다.

이 탭의 흐름

  1. 폐쇄형 시험 vs 오픈북 시험
  2. 키워드 검색이 놓치는 경우
  3. 의미를 좌표로 바꾸는 이유
폐쇄형 시험 (LLM 단독)
학생이 외운 지식만으로 답을 씁니다. 안 배운 내용, 최근 내용은 틀리거나 지어냅니다.
오픈북 시험 (RAG)
질문을 받으면 참고서에서 관련 페이지를 펼쳐 그 내용을 보고 답을 씁니다. 외우지 않아도 정확한 근거로 답합니다.
폐쇄형 (LLM 단독)   질문 ─────────────────→ LLM ──→ 아는 범위에서 답

오픈북 (RAG)        질문 ─→ [관련 자료 검색] ─→ 근거 + 질문 ─→ LLM ──→ 근거 기반 답
중요한 구분

모델을 다시 학습(재훈련)시키는 것은 “머릿속에 새로 외우게 하는 것”이고, RAG는 “시험장에 자료를 반입하게 하는 것”입니다. 문서가 자주 바뀌는 실무에서는 매번 외우게 하는 것보다, 그때그때 찾아보게 하는 편이 빠르고 저렴합니다.

“관련 자료 검색”이 왜 어려운가

키워드 검색이 놓치는 경우
문서: “프레스 작업 시 방호장치를 설치한다.”
질문: “기계에 손이 끼이지 않게 하려면?”

→ 겹치는 단어가 없어 못 찾을 수 있습니다.
사람은 어떻게 아는가
사람은 “방호장치 설치”와 “손 끼임 방지”가 의미상 같은 이야기임을 압니다.

→ 기계도 이 “의미의 유사성”을 계산할 수 있어야 합니다.

그래서 의미를 숫자로 바꿉니다

이렇게 풀어서 설명합니다

기계는 “비슷하다”를 직접 느끼지 못합니다. 대신 숫자 사이의 거리는 정확히 계산할 수 있습니다. 그래서 문장의 의미를 여러 개의 숫자, 즉 좌표(벡터)로 바꾸고, 의미가 비슷한 문장은 좌표도 가깝게 놓이도록 만듭니다.

문장 ──(임베딩 모델)──→ 벡터(숫자 좌표) ──→ 좌표 사이 거리로 "의미의 가까움"을 계산

"방호장치를 설치한다"   → [0.91, 0.82, 0.10]  ┐  두 좌표가 가까움
"손이 끼지 않게 한다"   → [0.89, 0.80, 0.12]  ┘  → 의미가 비슷하다고 판단
모든 개념의 뿌리

문장 → 임베딩 → 벡터 → 거리 계산. 이 한 줄이 이후 모든 탭의 바탕입니다. 03탭에서 실제 좌표와 계산으로 확인합니다.

03. 대상을 숫자로 표현하기 — 거리로 비슷함 재기

사람 세 명을 커피 선호도와 운동 선호도, 두 숫자로 표현해 봅니다. 특징을 수치화하면 두 대상이 얼마나 비슷한지를 거리 계산으로 판단할 수 있습니다.

거리가 작을수록 두 대상은 비슷합니다. A와 B는 성향이 거의 같아 가깝고(1.00), C는 취향이 반대라 멀리(9.90) 떨어져 있습니다. 문장도 똑같은 방식으로 좌표를 만들어 거리를 잽니다. 축이 2개가 아니라 수백 개일 뿐입니다.

Q. A3-M2(FAISS)에서 한 L2 거리와 같은 건가요?

같습니다. FAISS IndexFlatL2는 이 거리의 제곱(√를 빼고)을 돌려줬습니다. 순서는 똑같습니다. 제곱근은 순서를 바꾸지 않기 때문입니다.

04. 임베딩과 차원 — 문장을 숫자로, 몇 개의 숫자로

사람이 항목마다 점수를 매기는 대신, 임베딩(Embedding) 모델이 문장의 의미를 반영한 여러 숫자를 자동으로 만듭니다. 그 숫자의 개수가 차원(Dimension)이고, OpenSearch 설정과 반드시 맞아야 합니다.

이 탭의 흐름

  1. 임베딩 = 문장 → 숫자 배열
  2. 차원 = 숫자의 개수, 의미의 축
  3. 대표 모델의 차원
  4. 트레이드오프와 가장 흔한 실수
"프레스 방호장치를 설치해야 합니다."
                 ↓
           Embedding 모델   (문장의 의미를 학습한 모델)
                 ↓
      [0.91, 0.82, 0.10, ...]   ← Vector(벡터)
예시 값입니다

위 좌표값은 이해를 돕기 위한 예시입니다. 실제 임베딩은 사람이 해석하기 어려운 수백~수천 개의 숫자이며, “의미가 가까운 문장은 좌표도 가깝다”는 성질만 보장됩니다.

차원(Dimension)

이렇게 풀어서 설명합니다

벡터 하나에 들어 있는 숫자의 개수가 차원입니다. [9, 8]은 2차원, [0.91, 0.82, 0.10]은 3차원입니다. 각 숫자는 “의미를 이루는 하나의 축”이라고 이해하면 됩니다.

03탭의 사람 예시는 축이 2개라 취향을 대략적으로만 구분했습니다. 축을 수백~수천 개로 늘리면 “격식/캐주얼”, “긍정/부정”, “기계안전/화재안전”처럼 수많은 미세한 의미 성분을 동시에 담습니다. 이 축들은 사람이 지정하지 않고, 임베딩 모델이 대량의 텍스트를 학습하며 스스로 잡아냅니다.

실무에서 가장 자주 실수하는 제약

검색이 성립하려면 임베딩 모델의 출력 차원과 OpenSearch 벡터 필드의 dimension이 정확히 일치해야 합니다. 차원이 다른 벡터끼리는 거리 계산 자체가 불가능합니다. 그래서 저장할 때와 질문할 때 반드시 같은 모델을 쓰고, 모델을 바꾸면 저장된 벡터를 전부 다시 만들어야 합니다. 미션 7에서 이 오류를 일부러 내 봅니다.

Q. 그럼 무조건 큰 차원이 좋은가요?

아닙니다. 차원이 지나치게 커지면 “모든 벡터 사이 거리가 서로 비슷해져” 구별이 어려워지는 차원의 저주가 나타납니다. 보통 모델이 권장하는 차원을 그대로 쓰고, 데이터가 많아 느려지는 문제는 차원을 줄이는 대신 10탭의 ANN·HNSW 인덱스로 해결합니다.

05. 저장·검색 시스템의 필요 — 원문 + 벡터 + 메타데이터

문장을 벡터로 만들었다면, 그 벡터를 저장하고 질문과 가까운 벡터를 빠르게 찾아 줄 시스템이 필요합니다. 실제로는 벡터만이 아니라 원문 + 벡터 + 메타데이터를 한 문서로 함께 저장합니다.

Chunk 원문  "프레스 작업 시 방호장치를 설치해야 합니다."
     ↓ Embedding
Vector      [0.91, 0.82, 0.10]
     +
Metadata    source=press_safety.pdf · page=12 · type=안전지침 · year=2026
     ↓
Vector DB / Vector Search Engine (예: OpenSearch)
이렇게 풀어서 설명합니다

A3-M2에서 FAISS를 쓸 때는 벡터만 FAISS에 넣고, 원문은 docs.json, 카테고리는 따로 표로 들고 있었습니다. OpenSearch에서는 이 셋이 한 문서의 필드입니다. A4-M1의 sales 문서에 region, revenue가 같이 있던 것과 같고, 거기에 embedding 필드 하나가 더 붙을 뿐입니다.

메타데이터를 함께 두는 이유

“2026년 안전지침 중에서만 검색”처럼 조건을 건 의미 검색이 가능해집니다. 11탭(Filter)과 16탭(Python)에서 다시 다룹니다.

10. 대규모 검색 — Exact, ANN, HNSW

① Exact 검색은 왜 부담스러운가

Exact k-NN

“진짜 정답 top-k 중 몇 개를 실제로 찾아냈는가”입니다. 진짜 최근접 10개 중 9개를 찾으면 recall = 0.9. ANN의 목표는 recall을 1.0에 가깝게 유지하면서 속도를 얻는 것입니다.

11. Hybrid Search와 Metadata Filter

의미 검색이 강력해도 법령번호·모델명·사번·품번처럼 글자 자체가 중요한 검색에서는 키워드 검색이 더 정확합니다. 그래서 둘을 섞습니다(Hybrid). 그리고 조건으로 범위를 먼저 좁힙니다(Filter).

이 탭의 흐름

  1. 가중치 α로 키워드·벡터 섞기 (위젯)
  2. OpenSearch에서 섞는 방법 미리보기
  3. Metadata Filter
Hybrid Search 가중치 블렌더실시간 계산

결합 점수 = α × 벡터점수 + (1−α) × 키워드점수. α=0이면 키워드만, α=1이면 의미만 사용합니다.

이렇게 풀어서 설명합니다

α를 0으로 내리면 “제38조”라는 글자가 정확히 들어간 D1이 1등, 1로 올리면 표현은 달라도 뜻이 가까운 D2가 1등입니다. 중간에서는 양쪽 점수가 고른 D3가 강세입니다. 실무 질문에는 둘이 섞여 있으니 둘 다 씁니다.

OpenSearch에서는 키워드 검색(BM25)과 벡터 검색(k-NN)을 한 요청에 넣고, search pipeline이 두 점수를 0~1로 맞춘 뒤 가중 평균을 냅니다. 위젯의 α가 pipeline의 weights입니다. 17탭에서 실제로 만듭니다.

Metadata Filter

질문 "프레스 사고 예방 방법"
        ↓
Filter   year=2026 · factory=화성 · type=안전지침
        ↓
조건에 맞는 문서 집합 → Vector k-NN → Top-3 Chunk
벡터 유사도만큼 메타데이터 설계가 중요합니다

문서명·날짜·부서·페이지·문서종류·보안등급을 함께 저장하는 이유입니다. OpenSearch에서는 필터를 knn 쿼리 안의 filter에 넣어야 “조건 안에서 k개”가 채워집니다. 밖에서 거르면 0건이 될 수 있습니다(16탭).

import math

def chunk_text(text, size=200, overlap=40):
    if overlap >= size:
        raise ValueError("overlap은 size보다 작아야 합니다")
    stride = size - overlap
    n = 1 if len(text) <= size else math.ceil((len(text) - overlap) / stride)
    return [text[i * stride : i * stride + size] for i in range(n)]

chunks = []
for p in PAGES:
    for i, piece in enumerate(chunk_text(p["text"])):
        meta = {k: v for k, v in p.items() if k != "text"}
        chunks.append({"chunk_id": f'{p["doc_id"]}-p{p["page"]}-{i}', "chunk_no": i, "text": piece, **meta})

print("Chunk 수:", len(chunks))
for c in chunks[:3]:
    print(c["chunk_id"], "|", c["text"][:50], "...")

def search(question, k=3, filters=None, ef_search=None):
    knn = {"vector": embed_query(question), "k": k}
    if filters:
        knn["filter"] = {"bool": {"filter": [{"term": {f: v}} for f, v in filters.items()]}}
    if ef_search:
        knn["method_parameters"] = {"ef_search": ef_search}
    res = client.search(index=INDEX, body={
        "size": k,
        "_source": {"excludes": ["embedding"]},
        "query": {"knn": {"embedding": knn}},
    })
    return [{"score": round(h["_score"], 4), **h["_source"]} for h in res["hits"]["hits"]]

def make_pipeline(name, w_keyword, w_vector):
    body = {"phase_results_processors": [{"normalization-processor": {
        "normalization": {"technique": "min_max"},
        "combination": {"technique": "arithmetic_mean",
                        "parameters": {"weights": [w_keyword, w_vector]}},
    }}]}
    client.transport.perform_request("PUT", f"/_search/pipeline/{name}", body=body)

make_pipeline("hybrid-pipe", 0.3, 0.7)

def hybrid_search(question, k=3, pipeline="hybrid-pipe"):
    body = {
        "size": k,
        "_source": {"excludes": ["embedding"]},
        "query": {"hybrid": {"queries": [
            {"match": {"text": question}},                                   # 키워드 (weights 첫 번째)
            {"knn": {"embedding": {"vector": embed_query(question), "k": k}}},  # 벡터 (weights 두 번째)
        ]}},
    }
    res = client.search(index=INDEX, body=body, params={"search_pipeline": pipeline})
    return [{"score": round(h["_score"], 4), **h["_source"]} for h in res["hits"]["hits"]]

def rag_answer(question, k=3, filters=None, use_llm=True):
    vec_hits = search(question, k=k, filters=filters)
    if not vec_hits or vec_hits[0]["score"] < MIN_SCORE:
        return "관련 근거를 찾지 못했습니다. 담당자에게 문의해 주세요.", []
    prompt = build_prompt(question, vec_hits)
    answer = generate(prompt) if use_llm else prompt
    return answer, [(h["source"], h["page"]) for h in vec_hits]
