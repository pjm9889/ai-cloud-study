01. 완성된 A1 서비스를 다시 검증해야 하는 이유

A1-M6까지 작업하여 CSV 기반 웹 정합성 검사·검색 서비스가 이미 동작합니다. 사용자는 HTML을 입력하고 규칙 기반 판정과 관련 규칙 검색 결과를 확인하며 검사 이력을 조회할 수 있습니다. 이번에는 이 기능을 다시 구현하지 않습니다. Codex가 코드를 변경하는 과정과, 서버가 사용자에게 결과를 돌려주는 순간에 각각 어떤 오류가 가능한지를 구분하고 실제로 차단하는 것이 목표입니다.

1. 실제 운영 요청에서 생기는 두 가지 문제

가령 개발팀에서 “링크 검사 결과에 근거 규칙을 표시해 달라”고 요청했다고 가정합니다. 담당자는 A1의 rules.csv와 rule_tree.csv가 이미 규칙의 기준 원본이라는 점을 알고 있습니다. 그런데 Codex에게 화면 표시를 맡기면서 이 조건을 명시하지 않으면 다음 문제가 가능합니다.

발생 시점 바뀐 부분 외관상 결과 실제 실패
개발 중 Codex가 proposed 규칙을 applied로 수정 검사 규칙이 늘어나 동작하는 것처럼 보임 승인되지 않은 사내 규칙을 현행 기준으로 적용
응답 생성 중 검색 후보의 rule_id를 판정 결과의 규칙 ID로 사용 관련 규칙 설명이 그럴듯하게 출력됨 검색 추천과 규칙 엔진의 판정이 뒤섞임
응답 변조·버그 존재하지 않는 FAKE-999를 근거로 표시 사용자는 근거 있는 판정이라고 오해 실제 CSV에 없는 규칙을 인용
저장 직전 검증 없는 결과를 MySQL에 먼저 기록 이력 조회 기능은 정상 잘못된 결과가 영속 데이터로 남음

한 가지 테스트로 네 문제를 모두 막기 어렵습니다. 첫 번째는 개발 변경 검증, 나머지는 실행 시점의 응답 검증이 필요합니다. 이처럼 검증을 어디에 배치할 것인지가 하네스 설계의 출발점입니다.

2. 이번 실습에 이미 존재하는 코드와 데이터

프로젝트 루트는 ZIP 내부의 A1-M6_CSV통합실습/입니다. 파일명만 말하고 지나가지 않도록, 실제 쓰임을 먼저 확인합니다.

실제 경로 책임 이번에 보호할 업무 계약
data/rules.csv 판정 규칙 원본: 전체 8개, applied 7개, proposed 1개 현행 검사에는 applied만 포함
data/rule_tree.csv 규칙 분류 계층과 file·rule_id 참조 실존 규칙만 올바른 트리 노드에 연결
checker.py HTML을 규칙별로 판정 failed는 자체 규칙 실패이며 공식 인증 결과가 아님
search_engine.py TF-IDF·BM25로 관련 규칙 후보 반환 검색 점수는 판정 결과가 아님
pipeline.py 검사·검색·전처리·버전 캐시를 통합 직접 규칙과 참고 후보 분리
gold/, evaluate_baseline.py M4 평가 정답과 기준선 점수를 높이려고 정답셋을 몰래 변경하지 않음
db.py, api.py 검사 이력·웹 응답 검증 통과 결과만 저장·제공하는 방향으로 확장

예를 들어 LINK-002의 cantTell 결과는 주변 문맥을 확인해야 한다는 검사 엔진의 결과이고, BM25가 찾아 준 다른 규칙은 검토에 도움이 되는 참고 자료입니다. 높은 점수로 검색된 규칙을 LINK-002 대신 기록하면 안 됩니다.

3. 이번에 새로 추가하는 하네스 자산

harness_a1/ 폴더와 AGENTS.md, .agents/skills/a1-quality-gate/SKILL.md는 기존 A1-M6를 수정하지 않고 덧붙이는 실행·검증 계층입니다. 별도의 YAML, 규칙 변경 이력 CSV, 신규 LLM은 도입하지 않습니다.

개발 하네스 서비스 검증 하네스

SKILL.md — 재사용 검증 순서 guarded_api.py — DB 저장 전 검증 관문

성공의 정의는 간단합니다. 정상 응답은 통과시키고, 가짜 규칙·허위 출처·미승인 규칙·조작된 판정은 차단합니다. 반면 테스트가 통과했다는 사실로 WCAG 전체 적합성이 보증된다고 말해서는 안 됩니다.

02. 개발 하네스와 실행 하네스의 아키텍처

하네스는 새 AI 모델을 추가하는 것이 아니라 기존 AI 개발 작업과 서비스 응답을 둘러싸는 계약·도구·권한·검증 경계입니다. 여기에서는 “어떤 파일이 존재하나?”보다 “어느 순간에 무엇을 확인해야 하나?”를 기준으로 구조를 읽어 보겠습니다.

1. 개발 경로: Codex가 코드를 변경하는 순간

COMP-LINK-001 규칙의 금칙어를 바꾸라는 요청이 들어왔다고 가정합니다. Codex가 파일을 수정하기 전에 확인해야 할 내용은 다음과 같습니다.

단계 해당 하네스 결정하는 내용 잘못되면 어떻게 하나?
요청 해석 AGENTS.md CSV 원본·정답셋은 승인 없이 변경 금지 범위·영향부터 보고하고 변경 보류
검증 절차 선택 SKILL.md 변경 종류에 따라 어떤 테스트를 수행할지 호출 여부보다 실제 검증 명령 실행 기록 요구
기준 자산 감사 audit.py 규칙 7개와 검색 문서 7개·트리 참조의 일치 차이 위치를 표시하고 결과 제출 중단
회귀 검증 pytest 기존 검사·검색·API 계약이 유지됐는가 수정·재검증 또는 보류
완료 보고 Codex 결과 수정 파일과 테스트의 실제 증거 증거 없는 “완료” 주장 불인정

AGENTS.md는 행동을 유도하는 프로젝트 지침이지 OS 파일 권한이 아닙니다. 지침의 ‘수정 금지’와 파일 시스템의 실제 쓰기 제한은 다른 층입니다. 또한 Skill은 검사 스크립트의 호출 방법을 안내하지만, 검증 스크립트 실행 없이 결과를 보증하지 않습니다.

2. 실행 경로: 실제 검사가 끝난 뒤 DB에 쓰기 전에

이미 만들어진 InspectionService.inspect(html, method, k)는 검사 결과를 딕셔너리로 반환합니다. 이 결과를 곧바로 Store.save()에 저장하면 프로그램 오류가 있는 결과까지 이력으로 남을 수 있습니다.

이번 실습의 guarded_api.py는 검사 → 응답 계약 검증 → 저장 → 반환 순서를 강제합니다.

실습 코드·출력
result, cache_hit = service.inspect(body.html, body.method, body.k)
problems = verify(result, html=body.html, base=ROOT)
if problems:
    # 잘못된 결과를 DB에 넣기 전에 중단
    raise HTTPException(503, "검사 결과 검증 실패")
run_id = store.save(result, cache_hit)
return {**result, "run_id": run_id, "cache_hit": cache_hit}

이것은 원본 guarded_api.py의 흐름을 읽기 쉽게 줄인 설명용 코드입니다. 실제 파일에는 인증·예외 처리·로그가 추가돼 있습니다. 중요한 것은 store.save()가 verify() 이후에만 호출된다는 순서입니다.

3. 어떤 값이 정답의 기준인가?

정보 기준 데이터 왜 필요한가
존재하는 규칙 ID rules.csv의 applied 규칙 가짜 규칙과 검토 중 규칙 차단
각 규칙의 출처·범위 reference_url, scope, rule_version 사내 규칙을 WCAG 인증 결과로 오해하지 않게 함
HTML 요소의 판정 동일 HTML을 checker.scan()으로 재검사한 결과 숫자 요약을 같이 조작한 판정도 감지
원본 규칙과 검색 문서 연결 rule_tree.csv, build_documents() 검색 후보의 출처 추적
평가의 기준 정답 gold/ 아래 정답 CSV 테스트 통과를 위해 정답을 수정하는 편법 방지

핵심은 검증 기준이 검증하려는 결과에서 독립적이어야 한다는 것입니다. result['ok']가 True라는 선언은 정답 근거가 될 수 없습니다. 반면 CSV의 현재 규칙과 동일 HTML의 재검사 결과는 규칙 ID·상태·판정을 대조할 수 있는 별도 자료입니다.

다만 같은 checker.scan()을 다시 사용하는 검증은 그 검사기 자체에 있는 논리 오류까지 검출하지는 못합니다. 이를 확인하려면 A1-M4의 독립 정답셋과 회귀 테스트를 병행해야 합니다. 이 한계를 명시하는 것이 실무적인 하네스 설계입니다.

4. 오류 처리 정책은 어느 수준에서 결정할까?

문제가 난 곳 현재 구현의 처리 서비스 관점의 이유
요청 옵션 부적합 FastAPI 입력 검증/400 잘못된 사용자 입력과 서버 결함 구분
내부 검사 결과 계약 위반 verify가 오류 목록 생성, API는 503 잘못된 답을 정답으로 반환하거나 저장하지 않기 위해
원본 CSV 기준 해시 변경 audit가 실패로 종료 승인된 규칙 버전인지 확인 전 배포 중단
검색이 낮은 점수를 반환 관련성 신호일 뿐 판정 변경 금지 검색 신뢰도와 규칙 판정의 책임 구분

왜 모든 오류를 자동 재시도하지 않을까요? 규칙 ID가 원본에 없거나 승인 상태가 다른 오류는 다시 호출해도 해결되지 않을 가능성이 높습니다. 재시도보다 원본·버전·배포 문제를 먼저 진단해야 합니다.

5. 더 강화해야 할 경계와 현재 실습의 한계

이번 실습에는 rules.csv의 기준 SHA-256과 응답 재검사가 있지만, 실제 운영에서는 다음도 추가적으로 검토해야 합니다. 임의의 공격자가 규칙 CSV와 기준 해시 파일을 모두 바꿀 권한을 갖는다면 파일 해시 비교만으로는 신뢰성을 확보할 수 없습니다. 운영 기준점은 접근 제어와 승인된 릴리스·변경 이력에 의해 별도로 보호해야 합니다.

또한 동일 HTML을 재검사하면 처리 비용이 증가합니다. 실습에서는 계약 원리를 명확히 보기 위해 사용하지만, 운영에서는 변경 빈도·오류 비용에 따라 실행 전 정적 검증, 캐시 결과 검증, 중요 요청 재검사, 독립 평가 등을 조합해야 합니다.

설계 문제 — AGENTS.md에 금지 문구를 추가했는데도 규칙 CSV가 바뀌었다면 어느 층이 실패한 것일까요? 지침의 한계와 실제 권한·승인·감사 체계를 나누어 답해 보세요.

03. Codex 지침·Skill과 세 가지 검증 명령 실습

BLOCK | 존재하지 않는 직접 규칙 ID | DIRECT_EVIDENCE_MISMATCH: IMG-001

38 passed in 1.97s   # 예시 실행 환경에서 확인된 수치

BLOCK가 출력됐는데 왜 테스트는 성공인가?

demo.py는 의도적으로 나쁜 응답을 주입하는 실험입니다. 정상 응답은 PASS, 나머지 다섯 조작 응답은 BLOCK가 나와야 성공입니다. 반대로 존재하지 않는 규칙 ID가 PASS되면 하네스가 실패한 것입니다.

pytest -q의 통과는 이번 테스트에 포함한 계약들을 만족했다는 뜻이며, 운영 MySQL·가비아 K3s에서 정상 동작했다고 주장하는 뜻은 아닙니다.

04. 규칙 CSV·트리·검색 원본의 정합성 감사

A1에서 가장 위험한 데이터 오류는 CSV를 읽지 못하는 문법 오류만이 아닙니다. 데이터는 읽히지만 승인 상태가 잘못되거나 트리에서 다른 규칙을 가리키는 경우입니다. 이때 API는 정상 200을 반환해도 실제 업무 결과가 틀릴 수 있습니다.

1. 규칙의 생명주기를 데이터 계약으로 표현

실습 코드·출력

여기서 True는 단순히 두 리스트의 길이가 같다는 뜻이 아닙니다. 두 ID 집합이 같다는 의미입니다. 적용 규칙 7개와 검색 문서 7개라 해도 그중 하나의 ID가 다르면 동일한 상태라고 보지 않습니다.

2. 트리 CSV는 규칙 내용이 아니라 참조 경로입니다

A1-M2에서 rule_tree.csv는 계층 탐색을 위해 별도로 만들었습니다. 각 노드의 parent_id는 상위 분류를, 규칙 노드의 file과 rule_id는 실제 규칙 행의 위치를 표시합니다.

실습 코드·출력
rule_tree.csv의 규칙 노드
  ├─ node_id     : 트리 안에서 노드를 식별
  ├─ parent_id   : 상위 분류 노드를 가리킴
  ├─ file        : rules.csv
  └─ rule_id     : 실제 규칙 행의 rule_id

rules.csv의 해당 rule_id 행
  ├─ operator / values : 판정 함수·조건
  ├─ status            : 적용 여부
  └─ reason / reference_url : 설명과 출처

트리가 제공하는 경로는 검색·출처 추적을 위한 메타데이터입니다. 트리의 경로가 복잡하더라도 그 자체가 규칙을 실행하지 않습니다. 반면 존재하지 않는 rule_id를 가리키는 노드를 허용하면 나중에 사용자에게 원본 근거를 열어 줄 수 없으므로 감사에서 실패 처리합니다.

05. 응답 검증과 FastAPI 저장 차단 관문

이 절에서는 서비스 하네스가 구체적으로 어떤 값을 비교하는지 확인합니다. 웹페이지를 검사한 결과는 all_findings, review_items, summary처럼 여러 층의 데이터로 나뉩니다. 서로 일치하지 않는다면 하나의 값이 정상이어도 결과 전체를 믿어서는 안 됩니다.

1. 검사 결과 JSON을 먼저 관찰

다음 코드는 새로운 검사기를 만드는 코드가 아니라, 기존 결과를 조사하는 읽기 전용 실험입니다.

실습 코드·출력
python -m harness_a1.labs.guard_details
실습 코드·출력
첫 판정: {'target': 'I01', 'rule_id': 'IMG-001', 'outcome': 'failed', ...}
정상 응답: PASS
직접 근거 rule_id 변조: BLOCK
  - DIRECT_EVIDENCE_MISMATCH: IMG-001
판정만 변조: BLOCK
  - DETERMINISTIC_MISMATCH: 원본 HTML 재검사 결과와 차이
  - REVIEW_MISMATCH: 검토 대상 누락 또는 추가
  - SUMMARY_MISMATCH: ...

실습 코드를 보면 result를 바꾸기 전에 deepcopy()로 복사본을 만든 뒤 조작합니다. 정상 응답을 기준으로 같은 조건에서 한 필드만 변경해야 어떤 계약이 실패했는지 비교하기 쉽습니다.

2. runtime_guard.verify()의 검증 항목을 구분

검사 종류 비교 대상 검출하려는 오류
규칙 존재·상태 rule_id를 현재 applied 규칙에 조회 없는 ID·proposed를 현행으로 사용
규칙 범위·출처 scope, rule_version, reference_url 회사 정책과 표준 관련 검사를 혼동, 위조 출처
응답 개수 all_findings와 summary의 상태별 개수 요약 숫자 누락·조작
검토 목록 failed·cantTell 항목과 review_items 검토 대상 누락·추가
직접 근거 direct_rule.rule_id와 원 판정 ID 검색 후보를 직접 판정 근거인 것처럼 표시
결정적 재검사 동일 HTML을 checker.scan()으로 재판정 요약 숫자까지 맞춘 허위 판정

왜 요약 숫자만 검사해서는 안 될까?

예를 들어 원래 검사 결과에서 cantTell 하나를 failed로 바꾸고 요약의 두 숫자까지 변경하면, 단순 건수 검사는 일치합니다. 하지만 (target, rule_id, outcome)을 다시 계산한 결과와 비교하면 변경 사실을 검출할 수 있습니다.

다음 코드는 실제 검증 로직의 핵심 비교를 간추린 것입니다.

실습 코드·출력
expected = Counter(
    (f['target'], f['rule_id'], f['outcome'])
    for f in scan(html, rules)
)
seen = Counter(
    (f.get('target'), f.get('rule_id'), f.get('outcome'))
    for f in result['all_findings']
)
if seen != expected:
    issues.append('DETERMINISTIC_MISMATCH')

Counter를 사용하는 이유는 결과에 같은 튜플이 여러 번 존재하더라도 개수까지 고려해 비교하기 위해서입니다. 이는 검출 결과의 일관성 검사이며 checker.py 자체의 모든 오탐을 제거하는 검사는 아닙니다.

정상 검사 응답 PASS 현재 원본·출처·판정과 계약 일치

첫 줄의 정상 결과까지 차단되면, 하네스가 안전한 서비스를 만든 것이 아니라 정상 요청을 실패시키는 새로운 장애를 만든 셈입니다. 따라서 성공·실패 반례를 모두 검증해야 합니다.

4. FastAPI에 검증 관문을 배치하는 위치

기존 api.py는 남겨 두고, 실습은 harness_a1/guarded_api.py를 별도로 실행합니다. 이것은 이전 코드를 안전하게 비교할 수 있게 하는 교육용 대체 진입점입니다.

실습 코드·출력
# Windows PowerShell: 프로젝트 루트에서 실행
$env:APP_ENV = 'development'
$env:DATABASE_URL = 'sqlite:///./harness_demo.db'
python -m uvicorn harness_a1.guarded_api:app --host 127.0.0.1 --port 8000

브라우저에서 http://127.0.0.1:8000/을 열고 샘플 HTML을 검사합니다. POST /api/inspect가 정상이라면 run_id가 반환되고 이력 페이지에서 조회됩니다. 현재 코드는 개발용 SQLite 설정으로 실행한 것이며 운영 MySQL 연결을 검증한 결과는 아닙니다.

변조된 응답이 API에서 실제로 저장되지 않는지 확인하려면 두 번째 터미널에서 아래 명령을 실행합니다.

실습 코드·출력
python -m pytest harness_a1/tests/test_contract.py -k "guarded_api" -v

test_guarded_api_end_to_end는 정상 응답 HTTP 200과 이력 1건을, test_guarded_api_refuses_bad_response는 조작 응답 HTTP 503과 이력 0건을 확인합니다. 단, 이 테스트는 별도 임시 SQLite DB를 사용하므로 브라우저에서 열린 harness_demo.db의 이력을 조작하지 않습니다.

5. 오류·상태·출력의 책임을 구별해야 합니다

실습 구현은 내부 검증 실패를 HTTP 503으로 반환합니다. 이는 현재 서비스가 안전한 결과를 제공할 준비가 되지 않았다고 표현하기 위한 교육용 선택이며, HTTP 503이 모든 비즈니스 검증 오류에 항상 적합한 정답은 아닙니다. 사용자 입력 오류와 서버 결과 계약 실패를 동일한 코드로 취급하지 않아야 합니다.

현상 확인 지점 실무 대응
정상 응답도 503 verify가 반환한 오류 코드 기준 CSV·버전·응답 스키마 비교
테스트만 503이고 브라우저는 정상 의도적 실패 주입 테스트와 실제 앱을 구분 테스트의 임시 서비스 객체 확인
정상 응답인데 이력이 없다 Store.save() 호출·DB URL 200 처리 전 저장 오류 조사
출처 조작이 PASS runtime_guard.verify() 직접 근거 비교 회귀 테스트와 검증 기준 수정

완료 조건: 단순히 API가 열린 것을 넘어 정상 200·이력 1건, 조작 503·이력 0건이라는 서로 다른 결과를 증거로 설명할 수 있어야 합니다.

06. 캐시·평가·실패 대응을 운영 관점에서 검증

하네스는 잘못된 결과를 차단할 뿐 아니라, 변경 후 기존 기능이 유지되는지 확인하고 장애를 진단할 수 있어야 합니다. 이 절에서는 검증 관문이 새로 만든 부작용은 없는지 함께 살펴봅니다.

1. 캐시 적중과 검사가 실행됐다는 이력은 다릅니다

A1-M6의 pipeline.py는 동일한 HTML·규칙 CSV·트리·전처리 정책·검색 방식·Top-k에 대해 계산 결과를 재사용합니다. 반면 DB의 inspection_runs는 사용자의 검사 요청 기록입니다. 결과 계산을 재사용했더라도 검사 요청은 새로 기록될 수 있어야 합니다.

실습 코드·출력
python -m harness_a1.labs.cache_probe
실습 코드·출력
첫 계산 cache_hit: False
두 번째 계산 cache_hit: True
두 결과 동일: True
캐시 결과 계약 검증: PASS
주의: 여기서는 DB 저장을 하지 않는다. API 요청마다 run_id 저장 여부는 통합 테스트에서 확인한다.

이 실험은 파이프라인 계산 캐시만 검증합니다. 실제 DB 저장은 guarded_api.py의 API 통합 테스트에서 확인합니다. 이 둘을 한꺼번에 같은 것으로 설명하면 향후 검사 이력 누락을 발견하기 어렵습니다.

2. 버전이 바뀌면 캐시를 계속 써도 될까?

실습 코드·출력
# 기존 pipeline.py의 캐시 키 구성(핵심 항목)
key = (html_hash, rule_hash, tree_hash, preprocess_version, method, k)

rules.csv나 rule_tree.csv가 변경되면 다른 해시가 계산돼 새 캐시 결과를 만들도록 설계돼 있습니다. 여기서 중요한 업무 판단은 “언제 규칙을 변경해도 되는가”입니다. 캐시가 올바르게 무효화되어도 승인되지 않은 규칙이 적용되면 업무 실패입니다. 따라서 변경 승인 정책과 캐시 버전 정책을 별도로 설계합니다.

3. A1-M4 평가셋은 왜 수정 금지 자산인가?

현재 검색기·검사기를 고쳐 평가 점수가 떨어졌다고 가정합니다. 정답셋 gold/를 수정해 점수를 다시 올린다면 모델 성능이 좋아진 것이 아니라 검증 기준을 바꾼 것입니다. 정답 오류가 실제로 발견된 경우에는 수정 사유와 검토 절차를 남기고 평가 버전을 명확히 바꿔야 합니다.

실습 코드·출력
# 기존 A1의 동일 평가셋으로 검색·탐지 기준선 측정
python evaluate_baseline.py

# 변경 후 전체 회귀·원본 감사
python -m pytest -q
python -m harness_a1.audit

평가 지표가 높아도 서비스 응답 검증은 따로 필요합니다. 예를 들어 BM25가 정답 규칙을 잘 찾더라도 응답 생성 단계에서 FAKE-999를 인용하면 사용자는 잘못된 근거를 받습니다. 검색 품질과 인용 정합성은 서로 다른 품질 항목입니다.

3. 실무 이해도 평가

문제 1. `status=proposed` 규칙이 유사도 검색에서 높은 점수를 받으면 현행 규칙으로 사용해도 되는가?

아닙니다. 검색 점수는 관련성이고 적용 여부는 규칙 원본의 승인 상태입니다. 현행 검색 인덱스에서 제외하거나 별도 역사 조회로만 사용해야 합니다.

문제 2. `AGENTS.md`에 “CSV 삭제 금지”라고 적으면 실제 파일 쓰기가 차단되는가?

아닙니다. 지침은 에이전트의 행동을 안내하지만 파일 시스템·샌드박스·승인 정책의 강제 제약과 다릅니다.

문제 3. `demo.py`에서 BLOCK가 5개 나왔으므로 테스트가 실패한 것인가?

아닙니다. 의도적으로 조작한 다섯 결과가 차단돼야 검증 관문이 정상 동작한 것입니다. 정상 응답 1개는 PASS여야 합니다.

문제 4. `all_findings`의 개수와 `summary`가 일치하면 충분한가?

아닙니다. 판정과 요약을 함께 변조할 수 있으므로 동일 HTML과 규칙 CSV로 재검사한 `(target, rule_id, outcome)`까지 비교해야 합니다.

문제 5. `runtime_guard.verify`가 통과하면 WCAG 2.2 적합성 인증을 내릴 수 있는가?

아닙니다. 이 검증은 교육용 판정기의 규칙·출처·응답 정합성만 확인합니다. 전체 WCAG 요건을 평가하지 않습니다.

문제 6. `SOURCE_MISMATCH`가 발생하면 검색 1위 문서로 reference_url을 바꾸면 되는가?

안 됩니다. 판정 결과의 직접 출처는 해당 규칙의 CSV reference_url입니다. 관련 검색 후보의 출처와 교체할 수 없습니다.

문제 7. 계산 캐시가 적중했으므로 DB의 검사 이력도 추가하면 안 되는가?

아닙니다. 계산 재사용과 업무 요청 이력은 별개입니다. 현재 API는 검증 통과 후 요청별로 run_id를 기록하도록 되어 있습니다.

문제 8. 테스트가 모두 PASS인데 운영 DB에서 오류가 난다면 어떻게 판단하는가?

로컬 테스트 성공과 운영 환경 검증을 분리해야 합니다. 운영 네트워크·계정·권한·설정 차이를 따로 확인해야 하며 운영까지 검증됐다고 주장하지 않습니다.

4. 추가 응용 과제 — 기술을 한 단계 발전시키기

과제 작업 내용 합격 조건
A. 미승인 규칙 누출 검사 검색 결과에 proposed가 나타나는 가상 오류 설계 차단 코드와 원본 상태 필터 책임 설명
B. 가짜 근거 차단 direct_rule.rule_id를 바꿔 guard_details와 비교 직접 근거 불일치가 BLOCK됨
C. 요약 동반 조작 finding과 summary를 같이 바꾼 반례 분석 결정적 재검사에서 실패함
D. 캐시 정책 검토 입력·규칙·트리·전처리 버전의 역할 분석 규칙 변경 후 낡은 판정이 남지 않음
E. A2 인계 문서 벡터 검색·LLM이 추가될 때 새 검증 계약 제시 규칙 ID·출처·승인 상태를 계속 유지

6. 이후 A2에서 재사용할 계약

A2에서 Hugging Face 임베딩·FAISS·ChromaDB·OpenSearch·OpenAI API를 추가하더라도 A1의 기준 규칙과 출처는 유지됩니다. 다음 단계의 하네스에는 검색 근거 존재 여부, 규칙 ID 일치, 인용한 문서의 적용 상태, 응답 충실도, 비용·토큰 한도, 프롬프트 인젝션 방어를 더합니다.

중요한 경계: A2에서 검색이나 LLM이 좋아졌다고 해서 규칙 엔진의 결정적 판정을 임의로 덮어쓰지 않습니다. cantTell에 대해서만 근거 검색·추가 검토·판단 보류 등의 경로로 확장합니다.
