5요소 한눈에 보기

LangChain으로 LLM을 호출하는 코드는 항상 다섯 가지 요소로 이루어집니다. 이 단원은 아래 표의 다섯 줄을 하나씩 설명합니다.

순서요소하는 일
1모델 (Model)어떤 LLM을 어떤 설정으로 쓸지 정한다
2프롬프트 (Prompt)모델에 보낼 질문의 틀을 만든다. { }는 나중에 채울 빈칸
3출력 파서 (Output Parser)모델의 답을 원하는 형태(문자열 등)로 꺼낸다
4체인 (Chain)1~3을 파이프 |로 연결해 하나의 실행 단위로 만든다
5실행 (Invoke)빈칸에 값을 넣어 체인을 실행한다
# 1 모델
llm    = ChatOpenAI(model="gpt-4o-mini", temperature=0)
# 2 프롬프트
prompt = ChatPromptTemplate.from_template("당신은 {role} 전문가입니다. {question}")
# 3 파서
parser = StrOutputParser()
# 4 체인
chain  = prompt | llm | parser
# 5 실행
result = chain.invoke({"role": "건강", "question": "여름철식중독"})

왜 이렇게 다섯 개로 나누나

OpenAI SDK로도 질문 한 번은 보낼 수 있습니다. 그런데 하나의 코드 덩어리로 짜면 모델을 바꾸거나, 질문 틀을 고치거나, 답을 JSON으로 받거나, 검색 결과를 끼워 넣을 때마다 코드 전체를 손봐야 합니다. 다섯 요소로 나누면 바꾸고 싶은 부분 하나만 갈아 끼우면 됩니다.

바꾸고 싶은 것바꾸는 곳나머지
GPT → 클로드1 모델 한 줄그대로
질문 문장·역할2 프롬프트그대로
문자열 → JSON으로 받기3 파서그대로
검색 결과를 끼워 넣기(RAG)4 체인 앞에 부품 추가그대로
한 번 → 여러 개 동시 / 실시간 출력5 실행 메서드만그대로

데이터가 흘러가는 순서

코드에서 정의하는 순서(모델 → 프롬프트 → 파서)와 데이터가 지나가는 순서(프롬프트 → 모델 → 파서)는 다릅니다. 체인 prompt | llm | parser는 데이터가 지나가는 순서대로 씁니다.

해설 · 실무 관점
  • 품질 문제는 대부분 프롬프트와 파서에서 생깁니다. 모델은 한 번 정하면 거의 바꾸지 않습니다. "답이 이상하다", "형식이 깨진다"는 문제의 원인은 대개 무엇을 시켰는지(프롬프트)와 결과를 어떻게 받는지(파서)에 있습니다. 공부할 때도 이 두 요소에 시간을 가장 많이 쓰기를 권합니다.
  • LangChain이 모델을 똑똑하게 만들지는 않습니다. 같은 API 호출을 부품으로 정리해 줄 뿐입니다. 답의 품질은 여전히 프롬프트와 넣어 주는 데이터가 결정합니다. 이 점을 오해하면 "LangChain을 썼는데 왜 답이 별로지?"에서 막힙니다.
  • 타입 흐름(dict → ChatPromptValue → AIMessage → str)을 외워 두면 이후가 쉬워집니다. RAG·분기·멀티턴에서 나는 에러 대부분이 "앞 부품의 출력과 뒤 부품의 입력이 맞지 않음"입니다. 이 흐름을 알면 에러 메시지만 보고 어디가 어긋났는지 바로 읽힙니다.

전체 코드와 실행 결과

실습 노트북 첫 코드입니다. 주석 번호 ⓪~⑤가 이 단원의 탭 순서와 같습니다.

from dotenv import load_dotenv                                   # ⓪ .env 로더
from langchain_openai import ChatOpenAI                          # ① 모델
from langchain_core.prompts import ChatPromptTemplate            # ② 프롬프트
from langchain_core.output_parsers import StrOutputParser        # ③ 파서

# ⓪ .env 파일에서 API 키 불러오기
#    .env 파일에 OPENAI_API_KEY=키값 으로 적혀 있어야 함
load_dotenv()

# ① 모델
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# ② 프롬프트 — {role}, {question}은 실행할 때 채울 빈칸
prompt = ChatPromptTemplate.from_template(
    "당신은 {role} 전문가입니다. {question}에 답해주세요."
)

# ③ 출력 파서 — 모델의 답에서 글자만 꺼냄
parser = StrOutputParser()

# ④ 체인 — 프롬프트 → 모델 → 파서 순서로 연결
chain = prompt | llm | parser

# ⑤ 실행 — 빈칸 이름과 같은 키로 값을 넣음
data = {"role": "건강", "question": "여름철식중독"}
result = chain.invoke(data)
print(result)
여름철 식중독은 주로 고온다습한 날씨로 인해 발생하는 식품의 부패와 세균 증식으로 인해 발생합니다. 여름철에는 특히 다음과 같은 식중독 예방 수칙을 지키는 것이 중요합니다.

1. **식품 보관**: 냉장고의 온도를 4도 이하로 유지하고, 냉동고는 -18도 이하로 설정하세요. 음식은 가능한 한 빨리 냉장 보관하고, 상온에 방치하지 않도록 합니다.

2. **조리 전 손 씻기**: 음식을 조리하기 전과 후, 특히 생고기나 해산물을 다룬 후에는 반드시 손을 깨끗이 씻어야 합니다.

3. **조리 도구 소독**: 칼, 도마 등 조리 도구는 사용 후 깨끗이 세척하고 소독하여 교차 오염을 방지합니다.

여름철에는 특히 식중독의 위험이 높으므로, 이러한 예방 수칙을 잘 지켜 건강한 여름을 보내시기 바랍니다.

이 코드에서 확인할 것

  • data의 키 "role", "question"이 프롬프트의 빈칸 {role}, {question}과 이름이 같습니다. 이름이 다르면 에러가 납니다.
  • result는 문자열(str)입니다. 파서가 있기 때문입니다.
  • 모델에 실제로 전달된 문장은 "당신은 건강 전문가입니다. 여름철식중독에 답해주세요."입니다.
해설 · 실무 관점
  • 이 아홉 줄이 이후 모든 단원의 뼈대입니다. RAG는 프롬프트 앞에 검색 부품을 붙인 것이고, 분기는 이 체인을 여러 개 만들어 고르는 것이고, 멀티턴은 프롬프트에 이전 대화 자리를 하나 더 만든 것입니다. 새 단원에서 막히면 이 아홉 줄로 돌아와 무엇이 추가됐는지 비교해 보세요.
  • 권하는 습관: 체인을 만들면 먼저 prompt.invoke(data).to_string()을 찍어 봅니다. 모델이 실제로 받는 문장을 비용 없이 확인할 수 있고, 빈칸이 이상하게 채워지는 버그를 모델 호출 전에 잡습니다.
  • 출력 결과에서 모델이 "식품 보관 4도 이하" 같은 구체적 수치를 말합니다. 그럴듯하지만 근거 문서 없이 모델 지식으로 쓴 내용입니다. 의료 서비스라면 이런 답을 그대로 내보내지 않고, 근거 문서를 붙이는 RAG가 필요한 이유가 여기 있습니다.

API 키 등록

노트북 파일과 같은 폴더에 .env 파일을 만들고 아래처럼 한 줄을 적습니다. 따옴표는 붙이지 않습니다.

OPENAI_API_KEY=sk-...

load_dotenv()를 실행하면 이 값이 환경변수로 등록되고, ChatOpenAI는 OPENAI_API_KEY라는 이름의 환경변수를 자동으로 찾아 씁니다. 그래서 코드에 키를 직접 쓰지 않아도 됩니다.

자주 나는 에러 OpenAIError: The api_key client option must be set ...
원인 ① .env 파일이 노트북과 다른 폴더에 있다 ② 변수 이름이 OPENAI_API_KEY가 아니다 ③ load_dotenv()를 ChatOpenAI(...)보다 나중에 실행했다
키를 코드에 쓰지 않는 이유 노트북을 공유하거나 깃허브에 올리면 키가 그대로 노출됩니다. .env 파일은 공유 대상에서 빼고, 깃허브를 쓴다면 .gitignore에 추가합니다.
해설 · 실무 관점
  • 교육 현장에서 가장 흔한 사고는 키 유출입니다. 노트북에 키를 직접 쓰고 그대로 공유하거나 깃허브에 올리는 경우입니다. 유출된 키는 다른 사람이 써서 요금이 청구됩니다. 처음부터 .env로 분리하는 습관을 들이는 것이 코드 한 줄보다 중요합니다.
  • 실습 계정에는 사용 한도를 걸어 두기를 권합니다. OpenAI 대시보드에서 월 사용 한도를 정해 두면, batch나 반복문 실수로 요청이 수백 번 나가도 피해가 제한됩니다.
  • 에러 메시지 "api_key client option must be set"은 거의 항상 .env 위치 문제입니다. 주피터는 노트북 파일이 있는 폴더 기준으로 찾는다는 점만 기억하면 대부분 해결됩니다.

1모델: ChatOpenAIRAGLangGraph 참고

어떤 LLM을 어떤 설정으로 쓸지 정하는 부품입니다. 이 객체를 만드는 것만으로는 API 호출이 일어나지 않고, 실행(invoke)할 때 호출됩니다.

from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

왜 모델을 객체로 따로 만드나

  • 설정을 한곳에 모음: 모델 이름, temperature 같은 설정이 이 한 줄에만 있습니다. 바꿀 때 여기만 고칩니다.
  • 교체가 쉬움: 회사가 달라도 모델 객체는 같은 방식(.invoke())으로 쓰므로, 이 줄만 바꾸면 나머지 코드는 그대로 동작합니다.
  • 만드는 것만으로는 비용이 없음: 요금은 invoke로 실제 요청을 보낼 때 발생합니다.

주요 설정값

인자의미실습 권장
model사용할 모델 이름"gpt-4o-mini" (저렴하고 빠름)
temperature답의 무작위성. 0이면 같은 질문에 거의 같은 답, 높을수록 답이 다양해짐상담·분류·요약·SQL: 0
문구·가사 등 창작: 0.7 안팎
max_tokens답의 최대 길이(토큰 수)비용을 제한할 때
timeout응답 대기 최대 시간(초)응답이 오래 걸릴 때

모델만 단독으로 실행해 보기

모델은 체인 없이도 실행할 수 있습니다. 문자열을 넣으면 됩니다.

response = llm.invoke("안녕하세요")
print(type(response))
print(response.content)
<class 'langchain_core.messages.ai.AIMessage'>
안녕하세요! 무엇을 도와드릴까요?

문자열을 넣으면 LangChain이 HumanMessage(사람 메시지) 하나로 바꿔 모델에 보냅니다. 결과는 문자열이 아니라 AIMessage라는 객체입니다. AIMessage 안에는 답 글자 외에 여러 정보가 들어 있습니다.

속성내용예
.content답 글자'안녕하세요! 무엇을 도와드릴까요?'
.usage_metadata사용한 토큰 수{'input_tokens': 9, 'output_tokens': 10, 'total_tokens': 19}
.response_metadata모델 이름, 종료 이유 등{'model_name': 'gpt-4o-mini-...', 'finish_reason': 'stop', ...}

토큰 수와 모델 이름 뒤 날짜는 실행 환경에 따라 다르게 나옵니다.

다른 회사 모델로 바꾸기

모델 줄만 바꾸면 프롬프트·파서·체인 코드는 그대로 쓸 수 있습니다.

모델 이름은 각 회사가 수시로 바꿉니다. 실습할 때 각 회사 문서에서 현재 이름을 확인합니다.

해설 · 실무 관점
  • 의료·분류·요약에서는 temperature=0을 기본으로 둡니다. 같은 질문에 답이 바뀌면 결과를 검증할 수도, 버그를 재현할 수도 없습니다. 이런 작업에서는 답의 다양성보다 재현성이 훨씬 중요합니다.
  • 결과가 안 좋을 때 비싼 모델로 먼저 바꾸지 마세요. 프롬프트 문제를 모델 성능으로 덮으면 비용만 늘고 원인은 남습니다. 저렴한 모델로 프롬프트·파서를 먼저 다듬고, 그래도 안 될 때 모델을 올리는 순서를 권합니다.
  • 모델을 한 줄로 바꿀 수 있다는 점은 실무에서 생각보다 자주 쓰입니다. 한 회사 API에 장애가 나면 다른 회사 모델로 돌리고(12단원), 비용을 줄이려고 쉬운 작업은 작은 모델에 맡깁니다. 이때 나머지 코드를 건드리지 않아도 되는 구조가 LangChain을 쓰는 실질적인 이유입니다.
  • usage_metadata의 토큰 수는 개발 중에 자주 확인하세요. 프롬프트가 길어지는 만큼 비용이 늘어나는 것이 숫자로 보입니다.

2프롬프트: ChatPromptTemplateRAG

모델에 보낼 질문의 틀입니다. 바뀌는 부분을 {이름}으로 비워 두고, 실행할 때 dict로 값을 넣습니다. 같은 틀로 질문만 바꿔 여러 번 쓸 수 있습니다.

from langchain_core.prompts import ChatPromptTemplate
prompt = ChatPromptTemplate.from_template(
    "당신은 {role} 전문가입니다. {question}에 답해주세요."
)
print(prompt.input_variables)      # 채워야 할 빈칸 목록
['question', 'role']

빈칸이 채워지는 모습 확인하기

프롬프트도 혼자 실행할 수 있습니다. 모델을 부르지 않으므로 비용이 들지 않습니다. 모델에 무엇이 전달되는지 확인할 때 씁니다.

pv = prompt.invoke({"role": "요리", "question": "파스타 면 삶는 법"})
print(pv)

차이는 문장을 언제 완성하느냐입니다. f-string은 그 줄이 실행되는 순간 완성된 문자열이 되고, ChatPromptTemplate은 빈칸이 남은 틀로 있다가 invoke할 때 채워집니다. 이 차이 때문에 할 수 있는 일이 달라집니다.

system과 human을 나누는 방법

prompt = ChatPromptTemplate.from_messages([
    ("system", "당신은 {role} 전문가입니다. 쉬운 말로 답하세요."),   # 규칙·역할
    ("human",  "{question}"),                                     # 이번 질문
])

왜 나누나

꼭 나눠야 하는 것은 아닙니다. from_template 하나로도 동작합니다. 나누면 다음이 좋아집니다.

  1. 규칙이 더 잘 지켜짐: 모델은 system 메시지를 지켜야 할 규칙으로, human 메시지를 이번 질문으로 구분하도록 학습되어 있습니다. "쉬운 말로", "진단하지 마라" 같은 규칙은 system에 둘 때 더 잘 지켜집니다.
  2. 사용자 입력에 덜 흔들림: 사용자가 질문에 "앞의 지시는 무시해"라고 써도, 규칙이 별도 메시지로 있으면 영향을 덜 받습니다.
  3. 대화 기억에 필요: 멀티턴에서는 system(규칙) → 이전 대화 → 이번 질문 순서로 메시지를 쌓습니다. 메시지가 나뉘어 있어야 그 사이에 이전 대화를 끼울 수 있습니다(10단원).
  4. 관리가 쉬움: 규칙은 고정이고 질문만 바뀝니다. 규칙을 고칠 때 system 한 곳만 봅니다.

넣을 수 있는 메시지 종류

쓰는 법만들어지는 메시지용도
("system", "...")SystemMessage역할·규칙·출력 형식 지시
("human", "...") 또는 ("user", "...")HumanMessage사용자 발화
("ai", "...") 또는 ("assistant", "...")AIMessage모델이 했던 답. 주로 예시(퓨샷)용

("placeholder", "{history}")메시지 여러 개위와 같지만 값을 안 넣어도 됨(생략 가능)

도구 실행 결과를 돌려주는 메시지(ToolMessage)도 있지만, 템플릿에 쓰지 않고 코드에서 메시지 리스트에 붙입니다(13단원).

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.messages import HumanMessage, AIMessage

    ("system", "당신은 {role} 전문가입니다. '진료과: ○○ / 이유: ○○' 형식으로 답하세요."),
    ("human", "무릎이 붓고 아파요"),                    # 예시 질문

해설 · 실무 관점
  • 프롬프트는 사실상 코드입니다. 문장 하나를 바꾸면 결과가 달라지므로, 코드처럼 한곳에 모아 관리하고 바꿀 때는 결과를 비교해야 합니다. 템플릿으로 분리해 두는 것이 그 출발점입니다. f-string으로 코드 여기저기에 흩어 놓으면 어떤 문장이 어떤 결과를 냈는지 추적하기 어렵습니다.
  • system과 human을 나누는 기준은 "바뀌는가"입니다. 매번 같은 역할·규칙·형식은 system에, 매번 바뀌는 질문은 human에 둡니다. 그리고 사용자가 입력한 문장은 system에 끼워 넣지 않습니다. system에 들어간 사용자 문장은 규칙처럼 취급될 수 있기 때문입니다.
  • 형식을 맞추고 싶을 때는 긴 설명보다 예시 한 쌍(human/ai)이 효과적인 경우가 많습니다. "진료과: ○○ / 이유: ○○ 형식으로"라고 길게 설명하는 것보다, 그 형식의 답을 한 번 보여 주면 모델이 더 정확히 따라 합니다.

3출력 파서: StrOutputParserRAG

모델이 돌려준 AIMessage에서 필요한 것만 꺼내 원하는 형태로 바꾸는 부품입니다. StrOutputParser는 답 글자(content)만 문자열로 꺼냅니다.

파서 없음: prompt | llm

r = (prompt | llm).invoke(data)
print(type(r).__name__)   # AIMessage
print(r.content)          # 글자는 .content로 꺼내야 함

파서 있음: prompt | llm | parser

r = (prompt | llm | parser).invoke(data)
print(type(r).__name__)   # str
print(r)                  # 바로 출력 가능

파서가 있으면 결과를 바로 문자열로 다룰 수 있습니다. 예를 들어 result[1:4]처럼 자르면 "름철"이 나옵니다(0번째 글자 "여" 다음부터). 파서가 없으면 결과가 AIMessage라서 이렇게 자를 수 없습니다.

.content로 꺼내면 되는데 왜 파서를 쓰나

  • 체인 결과 형태를 정해 둠: 체인의 결과가 항상 str로 나오므로, 다음 체인에 그대로 넘기거나(04단원) 화면에 바로 출력할 수 있습니다.
  • stream에서도 문자열 조각: 파서가 있으면 stream의 조각도 문자열로 나옵니다. 없으면 조각마다 .content를 꺼내야 합니다.
  • 형태를 바꾸기 쉬움: 답을 dict로 받고 싶으면 이 자리를 JsonOutputParser()로 바꾸면 됩니다. 앞의 프롬프트·모델 코드는 그대로입니다.

해설 · 실무 관점
  • 파서는 "LLM 출력은 믿을 수 없다"는 전제에서 출발합니다. 모델은 형식을 자주 어깁니다. 결과를 사람이 읽기만 하면 상관없지만, 프로그램이 이어받아 쓰면 형식 하나 어긋나는 것이 곧 에러입니다.
  • 고르는 기준: 사람이 읽을 답이면 Str, 프로그램이 쓸 답이면 Json(또는 11단원 구조화 출력). 이 단원의 세 예제가 정확히 이 기준을 보여 줍니다. SQL(프로그램이 실행)은 Str이지만 형식을 엄격히 지시했고, 판정(프로그램이 분기)은 Json, 안내문(사람이 읽음)은 Str입니다.
  • 결과를 코드가 쓰는 경우에는 파서 다음에 검증 단계를 꼭 둡니다. 3-1의 SELECT 검사, 3-2의 "경미일 때만" 분기가 그 예입니다.

3-1기본 파서로 Text-to-SQL

StrOutputParser로 받은 문자열을 그대로 SQL로 실행하는 예제입니다. 사용자가 자연어로 물으면 LLM이 SQL을 만들고, 그 SQL로 DB를 조회합니다.

자연어 질문→prompt→llm→StrOutputParser→ SQL 문자열 →DB 실행→결과표

#############################
import pandas as pd
import sqlite3

# 1. 준비된 CSV 파일 읽기
csv_file = "감기환자_진료데이터.csv"
df = pd.read_csv(csv_file)

# 2. 실제 파일 형태의 데이터베이스(.db) 연결 생성
# 실행하면 현재 폴더에 'medical_records.db' 파일이 실제로 만들어집니다.
db_file = "medical_records.db"

df.to_sql("./patients_history", conn, index=False, if_exists="replace")

# 4. 저장 완료 후 안전하게 연결 닫기
conn.close()

  • df.to_sql(테이블명, conn, ...): 데이터프레임을 테이블로 저장합니다. if_exists="replace"는 같은 이름 테이블이 있으면 덮어씁니다.

[단계 2] 프롬프트 6요소로 SQL 생성 → DB 조회

import os
import sqlite3
import pandas as pd
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

# 1. 프롬프트 6요소(맥락, 작업, 지시, 입력구조, 범위, 출력형식)를 반영한 고도화 프롬프트
system_prompt = """
[1. Context (맥락)]
너는 병원 진료 기록이 저장된 SQLite 데이터베이스를 관리하는 최고의 데이터 분석가이자 AI 엔지니어다.

[2. Task (작업)]
사용자의 자연어 질문을 분석하여, 데이터베이스에서 정확한 통계나 정보를 조회할 수 있는 최적의 SQLite 쿼리문(SELECT)을 생성하라.

[3. Input & Schema (입력 구조)]
조회할 테이블 이름은 'patients_history'이며, 컬럼 명세와 데이터의 실제 의미는 다음과 같다:
- 환자ID, 진료일자, 이름, 나이, 성별, 체온, 증상지속일, 처방, 진료구분, 진료내용
- 증상 (예: '두통/인후통/재채기', '오한/피로감/기침') -> 환자가 병원에 와서 호소한 주관적 '느낌/현상' 글
- 진단명 (예: '급성 비인두염', '급성 기관지염', '독감 의심', '상기도 감염') -> 의사가 최종적으로 내린 '병명/진단' 결과

[4. Instructions (상세 지시사항)]
- 사용자가 '독감 환자', '독감 의심 환자', '상기도 감염 환자' 등 구체적인 '병명'이나 '진단 결과'를 물어볼 때는, 반드시 '증상' 컬럼이 아닌 [진단명] 컬럼을 기준으로 조건절(WHERE)을 작성해야 한다.
- 예: '독감 의심 환자' -> WHERE 진단명 = '독감 의심' 또는 WHERE 진단명 LIKE '%독감%'

[5. Scale & Constraints (범위 및 제약조건)]
- 생각, 해설, 부연설명은 절대 출력하지 마라.
- 마크다운 문법 기호(```sql ... ```)는 절대 포함하지 마라.
- SQL 구문 내부에서 문자열 상수를 비교할 때는 반드시 싱글 쿼테이션(예: '독감 의심')을 사용하라.

[6. Output Format (출력 형식)]
오직 'SELECT'로 시작하여 세미콜론(';')으로 끝나는 실행 가능한 순수 SQL 한 줄 문자열만 반환하라.
"""

prompt = ChatPromptTemplate.from_messages([
    ("system", system_prompt),
    ("human", "{question}")
])

# 2. 파이프라인 조립 (LCEL)
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
output_parser = StrOutputParser()
text_to_sql_chain = prompt | llm | output_parser

# 3. 자연어 질문 던지기 및 SQL 생성
user_question = "60세 이상 환자 중에서 독감 의심 환자는 몇 명이야?"
print(f"🗣️ 유저 질문: {user_question}\n")

generated_sql = text_to_sql_chain.invoke({"question": user_question})
print(f"🤖 [AI 생성 쿼리]: {generated_sql}\n")
print("-" * 60)

# 4. 실제 DB 파일('medical_records.db') 검증 및 결과 꺼내오기
db_file = "medical_records.db"
csv_file = "감기환자_진료데이터.csv"

is_ready = True
conn = sqlite3.connect(db_file)
cursor = conn.cursor()
cursor.execute(
    "SELECT count(name) FROM sqlite_master WHERE type='table' AND name='patients_history'"
)

if cursor.fetchone()[0] == 0:
    print(f"⚠️ [안내] '{db_file}' 내에 테이블이 없어 '{csv_file}' 파일로 자동 빌드를 시도합니다...")
    if os.path.exists(csv_file):
        df_csv = pd.read_csv(csv_file)
        df_csv.to_sql("patients_history", conn, index=False, if_exists="replace")
        print("-> [성공] 테이블 생성 및 데이터 복구가 완료되었습니다.\n")
    else:

# 5. 안전한 부근에서만 조회 실행

왜 프롬프트 [5], [6]이 중요한가

결과를 코드가 그대로 실행하기 때문입니다. 모델이 "다음 쿼리를 실행하세요: ```sql ...```"처럼 설명이나 마크다운을 붙이면 pd.read_sql이 에러를 냅니다. 사람이 읽는 답이 아니라 프로그램이 받는 답이면, 출력 형식을 이렇게 엄격하게 지정합니다.

LLM이 만든 SQL을 그대로 실행할 때의 위험 프롬프트에 "SELECT만"이라고 써도 DELETE나 DROP이 나올 가능성을 0으로 만들 수는 없습니다. 실무에서는 두 가지를 더합니다.
# ① 읽기 전용으로 연결 — 쓰기 쿼리는 DB가 거부
conn = sqlite3.connect("file:medical_records.db?mode=ro", uri=True)

# ② 실행 전 검사 — SELECT 한 문장만 허용
sql = generated_sql.strip().rstrip(";")
if not sql.upper().startswith("SELECT") or ";" in sql:
    raise ValueError(f"허용되지 않는 쿼리: {generated_sql}")
해설 · 실무 관점
  • 이 예제의 핵심은 "숫자는 LLM이 아니라 DB가 센다"는 설계입니다. LLM에게 "독감 환자가 몇 명이야?"를 직접 물으면 그럴듯한 숫자를 지어낼 수 있습니다. LLM에게는 SQL을 쓰는 일만 맡기고, 세는 일은 DB가 하게 하면 숫자가 정확해집니다. 14단원의 통계 체인도 같은 발상입니다. RAG가 약한 "집계 질문"을 이렇게 해결합니다.
  • 정확도를 좌우하는 것은 프롬프트 [3]의 스키마 설명입니다. 컬럼 이름만 주면 모델은 "증상"과 "진단명"을 구분하지 못해 독감 환자를 증상 컬럼에서 찾습니다. 각 컬럼이 무엇을 뜻하는지, 값의 예가 무엇인지 적어 준 것이 이 결과를 만든 이유입니다. 실무에서 Text-to-SQL이 틀리면 프롬프트보다 스키마 설명을 먼저 보세요.
  • 학습용으로는 좋은 예제지만, 이 형태로 서비스에 쓰지는 않기를 권합니다. 최소한 읽기 전용 연결과 SELECT 검사를 넣고, 조회할 수 있는 테이블을 제한하고, 결과 행 수에 상한을 둡니다. 개인정보가 있는 테이블이면 이름 같은 컬럼은 아예 조회 대상에서 빼는 것이 안전합니다.
  • 결과가 "COUNT(*) 1"처럼 숫자 하나로 나왔습니다. 사용자에게는 이걸 다시 문장으로 바꿔 주는 체인을 하나 더 두면 자연스러운 답이 됩니다. 04단원 순차 체인으로 이어지는 지점입니다.

3-2JSON 파서로 판정 → 분기

1단계에서 LLM이 증상의 위험도를 JSON으로 판정하고, 2단계에서 그 값에 따라 다른 프롬프트로 안내문을 만듭니다.

증상→judge | llm | JsonOutputParser→ dict →if level == "응급"→emergency 또는 mild 체인→안내문
from langchain_core.output_parsers import JsonOutputParser

####################################
# 조건 분기 체인 — 판정을 JSON으로 받기
####################################

json_parser = JsonOutputParser()   # JSON 파서

# 1단계: 위험도 판정 (JSON으로 답하게 지시)
judge = ChatPromptTemplate.from_template(
    "다음 증상을 분석해서 반드시 JSON으로만 답해. 다른 설명은 절대 넣지 마.\n"
    '형식: {{"level": "응급 또는 경미", "reason": "판단 이유 한 문장"}}\n'
    "증상:\n{text}"
)

emergency = ChatPromptTemplate.from_template(
    "다음 증상은 응급 상황이야. 119에 연락하고 병원에 가라는 강한 경고문을 써줘:\n{text}"
)
mild = ChatPromptTemplate.from_template(
    "다음 증상은 경미해. 집에서 할 수 있는 관리법을 친절하게 안내해줘:\n{text}"
)

# ── 입력 ──
symptom = "갑자기 가슴이 심하게 조이고 왼팔이 저리며 식은땀이 난다"

# 1단계: JSON으로 판정 받기
verdict = (judge | llm | json_parser).invoke({"text": symptom})
print("【판정 결과(JSON)】")
print(verdict, "\n")
# 예: {'level': '응급', 'reason': '심근경색 의심 증상입니다'}

# 2단계: JSON의 level 값으로 분기
if verdict["level"] == "응급":
    result = (emergency | llm | parser).invoke({"text": symptom})
else:
    result = (mild | llm | parser).invoke({"text": symptom})

print("【안내】")
print(result)

왜 JSON으로 받나

판정을 문자열로 받으면 "응급입니다", "응급 상황으로 보입니다", "매우 위급합니다"처럼 표현이 매번 달라져 if로 비교할 수 없습니다. JSON 파서로 dict를 받으면 verdict["level"]을 정확한 값과 비교할 수 있습니다. 판단 이유(reason)도 별도 키로 함께 받아 기록할 수 있습니다.

코드에서 확인할 것

  • 두 파서를 함께 씀: 판정 체인은 json_parser(결과 dict), 안내문 체인은 parser(StrOutputParser, 결과 str)입니다. 같은 모델에 파서만 바꿔 끼운 것입니다.
  • 중괄호 두 번 {{ }}: JSON 예시의 중괄호는 빈칸이 아니라 글자이므로 겹쳐 씁니다. {text}만 빈칸입니다.
  • 코드블록도 처리: 모델이 ```json ... ```으로 감싸 답해도 JsonOutputParser가 벗겨내고 dict로 바꿉니다.
  • 분기는 체인 밖의 파이썬 if: 같은 일을 체인 안에서 하는 것이 08단원 RunnableBranch입니다.
안전한 쪽으로 분기하기 모델이 "level": "응급 가능성"처럼 형식을 어기면 위 코드는 else(경미)로 갑니다. 의료처럼 놓치면 위험한 판단은 반대로, 확실히 "경미"일 때만 경미 안내로 보냅니다. 
if verdict.get("level") == "경미":     # .get: 키가 없어도 에러 없이 None
    result = (mild | llm | parser).invoke({"text": symptom})
else:                                   # 응급·형식 오류·누락은 모두 응급 안내
    result = (emergency | llm | parser).invoke({"text": symptom})
해설 · 실무 관점
  • 이 구조가 중요한 이유: LLM은 판단만 하고, 결정은 코드가 합니다. 모델이 "응급"이라고 판정하면 어떤 안내를 보낼지는 if문이 정합니다. 이렇게 나누면 결정 규칙을 사람이 읽고 검증할 수 있습니다. 08단원 분기, 그리고 LangGraph의 조건부 연결(라우팅)이 모두 이 구조를 확장한 것입니다.
  • 의료 분기에서 기본값을 "경미"로 두는 것은 위험합니다. 응급을 경미로 잘못 보내는 비용이 반대 경우보다 훨씬 큽니다. 확실히 경미할 때만 경미로 보내고, 판정이 애매하거나 형식이 깨지면 응급 쪽으로 보내는 것이 원칙입니다(안전한 쪽으로 실패하기).
  • reason을 함께 받는 것은 좋은 설계입니다. 판정 결과와 이유를 기록해 두면, 나중에 오판 사례를 모아 프롬프트를 고칠 근거가 됩니다. 실무라면 이 값을 로그로 저장하기를 권합니다.
  • JsonOutputParser는 형식을 "요청"할 뿐 강제하지 못합니다. 형식이 꼭 지켜져야 하면 11단원의 with_structured_output이 더 확실합니다.

3-3체인 밖 함수: 개인정보 마스킹 + Gradio

LLM에 보내기 전에 주민번호·전화번호·이름을 정규식으로 가리고, 가린 내용만 모델에 보냅니다. 마스킹은 파이썬 함수로 체인 바깥에서 먼저 실행합니다.

진료기록 원본→mask_privacy()→ 가린 문자열 →prompt | llm | parser→환자 안내문
########################
# 정규식 - 기밀정보 마스킹 처리
############################
import re
import gradio as gr
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
parser = StrOutputParser()

prompt = ChatPromptTemplate.from_template(
    "다음 진료기록을 환자가 이해하기 쉽게 설명해줘:\n{text}"
)
chain = prompt | llm | parser

# ── 마스킹 함수 ──
def mask_privacy(text):
    text = re.sub(r"\d{6}-\d{7}", "******-*******", text)        # 주민번호
    text = re.sub(r"01\d-\d{3,4}-\d{4}", "010-****-****", text)  # 전화번호
    text = re.sub(r"환자:\s*\S+", "환자: ***", text)             # 이름
    return text

# ── Gradio 처리 함수 ──
def process(record):
    masked = mask_privacy(record)          # 1. 마스킹
    answer = chain.invoke({"text": masked}) # 2. 마스킹된 걸로 모델 호출
    return masked, answer                   # 3. 둘 다 반환

demo = gr.Interface(
    fn=process,
    inputs=gr.Textbox(lines=8, label="진료기록 원본 (주민번호·전화·이름 포함)"),
    outputs=[
        gr.Textbox(lines=8, label="🔒 마스킹 결과 (모델에 실제 전달된 내용)"),
        gr.Textbox(lines=8, label="📋 환자 안내문 (최종 결과)"),
    ],
    title="진료기록 안전 변환기",
    description="민감정보를 가린 뒤 모델에 전달합니다. 왼쪽에서 마스킹 결과를 직접 확인하세요.",
)
demo.launch()

왜 LLM에 보내기 전에 가리나

모델에 보낸 문장은 외부 서버로 전송됩니다. 답변에서 가리는 것으로는 이미 보낸 정보를 되돌릴 수 없으므로, 민감정보는 보내기 전에 지웁니다. Gradio 화면 왼쪽에 마스킹 결과를 보여 주는 이유도 "모델에 실제로 무엇이 갔는지" 사람이 확인하기 위해서입니다.

이 정규식이 놓치는 것

  • 하이픈 없는 번호: 7503121234567, 01012345678
  • 콜론 없는 이름: "환자 김민수", 본문 중간의 "김민수 님"
  • 이메일, 주소

정규식 마스킹은 형식이 정해진 정보(번호류)에는 강하고, 이름처럼 형식이 없는 정보에는 약합니다. 확장 방법은 이 단원의 미션에서 다룹니다.

다음 단계 지금은 process 함수가 마스킹을 먼저 부르는 방식이라, 누군가 chain.invoke를 직접 부르면 마스킹 없이 원본이 전송됩니다. 마스킹 함수를 체인 안으로 넣어 항상 실행되게 만드는 방법이 05단원 RunnableLambda입니다.
해설 · 실무 관점
  • 의료 데이터를 다룬다면 이 예제가 이 단원에서 가장 중요할 수 있습니다. 외부 API로 보낸 문장은 되돌릴 수 없습니다. 개인정보는 "모델에 보내기 전에" 처리한다는 원칙을 처음부터 몸에 익혀야 합니다.
  • 정규식은 1차 방어선일 뿐입니다. 번호류는 잘 잡지만 이름·주소·병원명처럼 형식이 없는 정보는 놓칩니다. 실무에서는 더 근본적으로, 애초에 이름 같은 식별 정보 칸을 LLM에 보내는 데이터에서 빼는 방식으로 설계합니다. 마스킹보다 "안 보내기"가 더 안전합니다.
  • Gradio 화면 왼쪽에 마스킹 결과를 보여 준 것은 좋은 설계입니다. 사람이 "모델에 실제로 무엇이 갔는지" 눈으로 확인할 수 있기 때문입니다. 보안 장치는 동작하는지 확인할 수 있어야 의미가 있습니다.
  • 이 코드의 약점은 마스킹이 process 함수에만 있다는 점입니다. 누군가 chain.invoke를 직접 부르면 원본이 그대로 나갑니다. 보안 처리는 "부르는 쪽이 잊지 않기"에 맡기지 말고 체인 구조에 넣어야 합니다(05단원).

4체인: 파이프 | 로 연결RAGLangGraph 필수

|(파이프)는 왼쪽 부품의 출력을 오른쪽 부품의 입력으로 넘깁니다. 이렇게 연결한 것을 체인이라고 하고, 이 문법을 LCEL(LangChain Expression Language)이라고 부릅니다.

chain = prompt | llm | parser

각 단계의 입력과 출력

단계받는 것 (입력)내보내는 것 (출력)
promptdict {"role": ..., "question": ...}ChatPromptValue (빈칸이 채워진 메시지)
llmChatPromptValue (또는 문자열·메시지 리스트)AIMessage
parserAIMessagestr

규칙: 앞 부품의 출력이 뒤 부품이 받을 수 있는 형태여야 합니다. 개수 제한은 없지만 이 규칙이 깨지면 에러가 납니다.

체인을 단계별로 쪼개 실행하기

체인 결과가 이상할 때는 한 단계씩 실행해 어디서 문제가 생겼는지 찾습니다.

data = {"role": "건강", "question": "여름철식중독"}
step1 = prompt.invoke(data);   print(type(step1).__name__)   # ChatPromptValue
step2 = llm.invoke(step1);     print(type(step2).__name__)   # AIMessage
step3 = parser.invoke(step2);  print(type(step3).__name__)   # str
# chain.invoke(data)는 위 세 줄을 한 번에 실행한 것과 같다

한 줄씩 invoke하면 되는데 왜 체인으로 묶나

위처럼 세 줄로 실행해도 결과는 같습니다. 체인으로 묶으면 다음이 가능해집니다.

  • 전체를 한 번에 stream · batch: chain.stream(), chain.batch()가 프롬프트부터 파서까지 한꺼번에 적용됩니다. 세 줄 방식으로는 직접 반복문을 짜야 합니다.
  • 더 큰 체인의 부품이 됨: 이 체인 자체를 다른 체인에 |로 이을 수 있습니다. RAG(07단원)와 분기(08단원)가 이렇게 만들어집니다.
  • 안전장치를 한 번에 씌움: 재시도·대체 모델(12단원)을 체인 전체에 적용할 수 있습니다.

순서를 잘못 연결하면

wrong = llm | prompt          # 모델 출력(AIMessage)을 프롬프트에 넣으려 함
wrong.invoke("안녕")
TypeError: Expected mapping type as input to ChatPromptTemplate. Received <class 'langchain_core.messages.ai.AIMessage'>.

에러 메시지 해석: "ChatPromptTemplate은 mapping(dict)을 기대했는데 AIMessage를 받았다." 프롬프트는 dict만 받기 때문입니다.

구버전 문법 주의 인터넷 자료에서 LLMChain(llm=llm, prompt=prompt), chain.run(...)을 보면 구버전입니다. 현재는 prompt | llm | parser와 .invoke()를 씁니다.
해설 · 실무 관점
  • |는 처음에 마법처럼 보이지만, 실체는 "앞 결과를 뒤에 넣기"입니다. 이 점만 확실하면 RAG 체인처럼 길어 보이는 코드도 왼쪽부터 한 칸씩 따라가며 읽을 수 있습니다.
  • 디버깅은 항상 체인을 쪼개서 합니다. 체인 전체 결과가 이상하면 앞에서부터 한 단계씩 invoke해 어디서 값이 틀어지는지 찾습니다. LangGraph에서도 노드를 하나씩 실행해 보는 방식이 같으므로, 지금 이 습관을 들여 두면 그대로 쓰입니다.
  • 긴 체인을 한 줄에 몰아 쓰기보다 의미 단위로 나눠 변수에 담기를 권합니다. 예: sql_chain = ..., answer_chain = ..., full = sql_chain | answer_chain. 각 조각을 따로 테스트할 수 있고 재사용도 쉽습니다.

5실행: invoke · stream · batchRAGLangGraph 참고

완성된 체인을 실행하는 방법은 세 가지이고, 모든 체인에서 똑같이 쓸 수 있습니다.

명령하는 일입력출력언제 쓰나
.invoke()한 번 실행입력 1개결과 1개가장 기본. 질문 하나 → 답 하나
.stream()답을 조각 단위로 실시간 출력입력 1개조각들(반복)ChatGPT처럼 글자가 차례로 나오게
.batch()여러 개를 한꺼번에입력 리스트결과 리스트질문 여러 개를 빠르게 동시 처리

invoke

result = chain.invoke({"role": "요리", "question": "파스타 면 삶는 법"})
print(result)

답이 다 만들어질 때까지 기다렸다가 한 번에 돌려줍니다.

stream

for chunk in chain.stream({"role": "요리", "question": "파스타 면 삶는 법"}):
    print(chunk, end="", flush=True)
  • 답이 만들어지는 대로 조각(chunk)을 하나씩 받습니다. 조각은 몇 글자 단위의 문자열입니다.
  • end="": 조각마다 줄을 바꾸지 않고 이어 붙입니다.
  • flush=True: 받은 즉시 화면에 표시합니다.
  • 전체 시간은 invoke와 비슷하지만, 첫 글자가 바로 나와 사용자가 덜 기다린다고 느낍니다.

batch

results = chain.batch([
    {"role": "요리", "question": "파스타 면 삶는 법"},
    {"role": "건강", "question": "여름철식중독"},
    {"role": "운동", "question": "허리 스트레칭"},
])
for r in results:
    print(r[:40], "...")
  • 입력 리스트를 넣으면 결과 리스트가 입력과 같은 순서로 나옵니다.
  • 내부에서 동시에 요청을 보내므로 for문으로 invoke를 세 번 하는 것보다 빠릅니다.
  • 요청이 너무 많아 에러(429)가 나면 동시 요청 수를 줄입니다: chain.batch(inputs, config={"max_concurrency": 2})
비용 invoke · stream · batch 모두 요청 1건당 쓰는 토큰은 같으므로 요금도 같습니다. batch는 빨라질 뿐 싸지지 않습니다. (OpenAI의 할인형 "Batch API"와는 다른 기능입니다.)
해설 · 실무 관점
  • 고르는 기준: 사용자 화면이면 stream, 데이터 일괄 처리면 batch, 개발·테스트는 invoke. 챗봇에서 invoke를 쓰면 답이 완성될 때까지 화면이 멈춰 있어 사용자가 오류로 오해하기 쉽습니다.
  • batch는 동시 요청 수를 작게 시작하세요. 수십 건을 한 번에 보내면 요청 한도(429 에러)에 걸리기 쉽습니다. max_concurrency를 2~5 정도로 두고 늘려 가는 것을 권합니다.
  • 세 메서드가 어떤 체인에도 똑같이 붙는다는 점이 중요합니다. 지금 만든 세 부품짜리 체인이든, 나중에 만들 RAG·분기 체인이든 사용법이 같습니다. 새 기능을 배울 때마다 실행법을 다시 배울 필요가 없습니다.

자주 묻는 질문

Q1. f-string으로 프롬프트를 만들면 안 되나요?

한 번 호출하고 끝나는 코드면 괜찮습니다. 체인으로 연결하거나, 같은 틀을 여러 값으로 반복하거나, 검색 결과를 끼우려면 ChatPromptTemplate이 필요합니다. ('2 프롬프트' 탭의 비교표)

Q2. system과 human을 꼭 나눠야 하나요?

필수는 아닙니다. 규칙을 더 잘 지키게 하고, 대화 기억을 넣으려면 나눕니다.

Q3. human 말고 어떤 메시지를 넣을 수 있나요?

system, human(user), ai(assistant), 이전 대화 자리(MessagesPlaceholder / placeholder)입니다. ai 메시지는 원하는 답 형식을 예시로 보여 줄 때 씁니다.

Q4. 파서 없이 .content로 꺼내면 안 되나요?

단독 호출이면 같습니다. 체인 결과를 다음 체인에 넘기거나, stream으로 받거나, 나중에 JSON으로 바꿀 계획이면 파서를 둡니다.

Q5. prompt.invoke → llm.invoke → parser.invoke를 차례로 하면 안 되나요?

결과는 같습니다. 체인으로 묶어야 stream · batch를 전체에 한 번에 쓰고, 더 큰 체인(RAG·분기)의 부품으로 쓸 수 있습니다.

Q6. temperature=0이면 항상 똑같은 답이 나오나요?

거의 같지만 완전히 같다고 보장되지는 않습니다. 같은 답이 꼭 필요한 곳(정답 비교, 테스트)은 결과를 저장해 두고 비교합니다.

Q7. ChatOpenAI(...)를 실행하면 요금이 나가나요?

아닙니다. invoke · stream · batch로 실제 요청을 보낼 때 나갑니다.

Q8. llm.invoke("안녕")처럼 문자열을 넣으면 내부에서 어떻게 되나요?

HumanMessage 하나로 바뀌어 모델에 전달됩니다. 프롬프트 템플릿을 거친 것과 같은 형태입니다.

Q9. batch를 쓰면 요금이 싸지나요?

아닙니다. 요청 수와 토큰이 같으므로 요금도 같고, 동시에 보내서 빨라질 뿐입니다.

Q10. 빈칸 이름은 아무거나 써도 되나요?

파이썬 변수 이름처럼 영문·숫자·밑줄로 짓습니다. 실행할 때 넣는 dict의 키와 철자가 정확히 같아야 합니다. 글자 그대로의 중괄호가 필요하면 {{ }}로 씁니다(02단원).

M9. Text-to-SQL 버그 고치고 안전장치 달기

체크포인트

예시 답안 보기
import sqlite3, pandas as pd

# ① 버그 수정
df = pd.read_csv("감기환자_진료데이터.csv")
with sqlite3.connect("medical_records.db") as c:
    df.to_sql("patients_history", c, index=False, if_exists="replace")
    print(c.execute("SELECT name FROM sqlite_master WHERE type='table'").fetchall())

# ②③ 안전 실행
def safe_query(sql: str) -> pd.DataFrame:
    s = sql.strip().rstrip(";").strip()
    if not s.upper().startswith("SELECT") or ";" in s:
        raise ValueError(f"허용되지 않는 쿼리: {sql}")
    conn = sqlite3.connect("file:medical_records.db?mode=ro", uri=True)   # 읽기 전용
    try:
        return pd.read_sql(s, conn)
    finally:
        conn.close()

for q in ["SELECT COUNT(*) FROM patients_history;", "DELETE FROM patients_history;", "SELECT 1; DROP TABLE x;"]:
    try:
        print(safe_query(q))
    except ValueError as e:
        print("차단:", e)

import re
def mask_privacy(t: str) -> str:
    t = re.sub(r"\d{6}-?\d{7}", "******-*******", t)            # 주민번호(하이픈 선택)
    t = re.sub(r"01\d-?\d{3,4}-?\d{4}", "010-****-****", t)     # 휴대폰(하이픈 선택)
    t = re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", "***@***", t)         # 이메일
    t = re.sub(r"환자\s*:?\s*[가-힣]{2,4}", "환자 ***", t)           # 환자 이름(콜론 선택)
    return t
